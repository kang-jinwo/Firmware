## 2. 정수 연산 (P5)

### 왜 정수로 바꾸는가

값싼 마이크로컨트롤러에는 실수 연산 장치(FPU)가 없다. `float` 곱셈 한 번을 정수 명령어 수십~백 개로 흉내 낸다 (소프트웨어 부동소수점). 정수 곱셈은 명령어 한 개다. 제어 주기 안에 끝내려면, 그리고 전력을 아끼려면 정수로 계산한다.

### 고정소수점: 소수를 정수에 담는 법

ki × dt × 1000 = 0.02 × 0.001 × 1000 = 0.02. 정수로는 0이다. 그대로는 담을 수 없다.

그래서 **미리 2^q 를 곱해서** 저장하고, 계산이 끝난 뒤 2^q 로 나눈다. q = 8 이면 256배.

```
실제 값      저장하는 정수 (× 1000 × 256)
kp = 0.002   →  512        (정확)
ki·dt = 0.00002 → 5.12 → 5  (2.3 % 작아진다)
```

100원 단위 대신 1원 단위로 장부를 쓰는 것과 같다. 눈금을 잘게 쪼개서 소수를 없앤다.

```c
c->integ_q += c->ki_q * e;              // 적분 (256배 된 채로 쌓는다)
u_q = c->kp_q * e + c->integ_q;         // 듀티 × 256
return clamp_duty(u_q >> c->q_shift);   // >> 8 : 오른쪽으로 8비트 밀기 = 256으로 나누기
```

2의 거듭제곱을 쓰는 이유: 나눗셈은 느리지만 비트를 미는 것(`>>`)은 명령어 한 개다.

변환(`controller_set_fixed_point`)은 시작할 때 한 번만 한다. 매 주기 도는 `control_pi_int` 안에는 `float` 가 하나도 없다.

### 두 가지 함정

**함정 1 — 눈금이 너무 굵으면 작은 값이 0이 된다 (반올림 오차)**

| q | ki_q (원래 값) | 저장되는 값 | 결과 |
|---|---|---|---|
| 4 | 0.32 | **0** | 적분이 사라진다 |
| 6 | 1.28 | 1 | ki 가 22 % 작아진다 |
| 8 | 5.12 | 5 | 2.3 % 작아진다 |
| 12 | 81.92 | 82 | 0.1 % |

**함정 2 — 눈금이 너무 잘면 큰 값이 넘친다 (오버플로)**

정수는 담을 수 있는 범위가 정해져 있다.

| 자료형 | 범위 |
|---|---|
| `int16_t` | −32,768 ~ 32,767 |
| `int32_t` | 약 −21억 ~ 21억 |

자리를 잡았을 때 적분 값은 듀티 0.337, 즉 337 × 2^q 다.

| q | 적분에 담겨야 하는 값 | `int16_t` 에 들어가나 |
|---|---|---|
| 6 | 21,568 | 들어간다 |
| 8 | 86,272 | **안 들어간다** |

2의 보수 표현에서 32,767 다음은 −32,768 이다. 값이 한 바퀴 돌아 반대편으로 넘어간다.

**정밀도를 올리면(q를 키우면) 범위가 모자라고, 범위를 지키면(q를 줄이면) 정밀도가 모자란다.** 고정소수점 설계는 이 둘 사이에서 q와 자료형을 고르는 일이다.

**Q2.** 16비트 적분기에서 q = 8 일 때 듀티가 톱니 모양이 되는 과정을 설명해 본다.

<details><summary>▶ 답과 설명 보기</summary>

1. 적분이 쌓인다. 필요한 값은 86,272 인데 32,767 까지만 담을 수 있다 (듀티로 0.128).
2. 32,767 을 넘는 순간 −32,768 근처로 넘어간다. 듀티의 적분 몫이 +0.128 에서 −0.128 로 한순간에 떨어진다.
3. 오차가 여전히 양수이므로 다시 쌓인다. 2로 돌아간다.

모터는 필요한 듀티 0.337 에 영영 닿지 못하고 271.8 근처에서 흔들린다.

실제 사고 사례가 많은 종류의 버그다. 평소 입력에서는 멀쩡하다가, 값이 어떤 크기를 넘는 날 갑자기 반대 방향으로 튄다. 막는 방법은 (1) 값의 최댓값을 미리 계산해 자료형을 고르고, (2) 더하기 전에 한계를 검사해 넘지 않게 자르는 것(포화 연산)이다.
</details>

**Q3.** `int32_t` 적분기는 안전한가? q = 8 일 때 넘치려면 적분이 얼마나 쌓여야 하는지 계산해 본다.

<details><summary>▶ 답과 설명 보기</summary>

한계 약 21억 ÷ 256 ÷ 1000 = 듀티 단위로 약 8,388. 필요한 값은 최대 1이다. 넉넉하다.

하지만 "넉넉해 보인다"와 "절대 넘지 않는다"는 다르다. 목표를 낼 수 없는 값(1500)으로 주면 적분이 1초에 6.24씩 계속 쌓인다 (M9의 P6). 8,388 ÷ 6.24 ≈ 1,340초, 약 22분 뒤에 넘친다. 22분 동안 켜 두는 테스트를 하지 않으면 발견하지 못한다.

q = 16 으로 올리면 한계가 듀티 단위 32.8이 되어 5초 만에 넘친다.

결론: 적분에 한계를 두어야 한다 (anti-windup, M9). 오버플로와 windup은 뿌리가 같은 문제다.
</details>

**Q4.** `c->kp_q * e` 에서 두 수의 곱이 넘칠 수는 없는가? (kp_q = 512, 오차의 최댓값을 생각해 본다)

<details><summary>▶ 답과 설명 보기</summary>

오차의 최댓값은 목표가 1500이고 속도가 0일 때 1500 정도다. 잡음까지 넣어 넉넉히 2000으로 본다.
512 × 2000 = 1,024,000. `int32_t` 범위 안이다.

하지만 kp 를 0.3 으로 하고 q = 12 로 하면 kp_q = 0.3 × 1000 × 4096 = 1,228,800. 여기에 2000을 곱하면 24.6억으로 21억을 넘는다.

곱셈은 덧셈보다 훨씬 쉽게 넘친다 (자릿수가 더해지므로). 고정소수점 코드에서는 곱셈마다 "두 수의 최댓값을 곱하면 얼마인가"를 따져야 한다. 귀찮지만 컴파일러가 대신 해 주지 않는다.
</details>

## 3. 타이밍 추정

### 식

```
루프 실행 시간 = 명령어 수 × CPI ÷ 클록 주파수
```

- 명령어 수: 루프 한 바퀴(`fw_tick`)에서 실행되는 기계어 명령어의 개수
- CPI (Cycles Per Instruction): 명령어 하나에 드는 평균 클록 수. 컴퓨터구조에서 배운 그 값
- 클록 주파수: 대상 마이크로컨트롤러의 값

### 명령어 수 세기 (직접 한다)

컴파일러가 만든 기계어를 본다.

```
gcc -std=c99 -O1 -c firmware/controller.c -o build/controller.o
objdump -d build/controller.o
```

`<control_pi_int>:` 아래에 나오는 줄 하나가 명령어 하나다. 함수별로 줄 수를 센다. `filter.c`, `firmware.c` 도 같은 방법으로 센다.

<details><summary>▶ 내가 센 값 (gcc 13, x86-64, -O1)</summary>

| 함수 | 명령어 수 (함수 전체) |
|---|---|
| `fw_tick` | 16 |
| `ma_update` | 25 |
| `control_pi_int` | 40 |
| `clamp_duty` | 8 |
| `control_pi` (float) | 35 |
| `control_p` | 10 |

컴파일러 버전에 따라 조금 다르다. 비슷한 크기면 된다.

주의: 이것은 함수에 **들어 있는** 명령어 수다. `if` 로 갈라지는 길 중 하나만 실행되므로 실제로 **실행되는** 수는 이보다 작다. 여기서는 넉넉하게(최악의 경우로) 전체를 센다.
</details>

### 타이밍 표

가정을 분명히 적는다. 가정이 바뀌면 답이 바뀐다.

- 대상: 16 MHz 클록의 작은 마이크로컨트롤러, FPU 없음
- CPI = 2 (가정)
- `sensor_read`, `pwm_set` 은 실제 보드에서 레지스터를 읽고 쓰는 짧은 함수로 보고 합쳐서 20개로 가정
- 명령어 수는 PC(x86-64)에서 센 값을 그대로 쓴다. 대상 CPU에서는 다르다 (아래 Q2)

| 항목 | 정수 PI | float PI (FPU 없음) |
|---|---|---|
| `fw_tick` | 16 | 16 |
| `ma_update` | 25 | 25 |
| 제어 함수 | 40 + 8 | 35 + 8, 그중 실수 연산 약 10번 × 100개 = 약 1,000 |
| HAL 두 함수 (가정) | 20 | 20 |
| **명령어 수 합계** | **약 110** | **약 1,100** |
| 실행 시간 (× 2 ÷ 16 MHz) | **약 14 µs** | **약 140 µs** |
| 제어 주기 1 ms 대비 | 1.4 % | 14 % |

(실수 연산 한 번에 100개라는 것은 어림값이다. 실제로는 덧셈, 곱셈, 나눗셈에 따라 수십~수백 개로 다르다.)

결론: 이 조건에서는 둘 다 1 ms 안에 든다 (검증 기준 V6 통과). 하지만 여유가 다르다.

- 클록이 1 MHz 인 더 작은 칩이라면: 정수 0.22 ms (통과), float 2.2 ms (**주기를 넘는다**).
- 제어 주기를 0.1 ms 로 줄여야 한다면: 16 MHz 에서도 float 는 넘는다.

그리고 N에 따라 실행 시간이 달라진다. 지금 방식(빼고 더하기)은 N이 얼마든 같다. 펌웨어에서는 "평균적으로 빠른 것"보다 **"언제나 같은 시간 안에 끝나는 것"** 이 더 중요할 때가 많다. 최악의 경우가 주기를 넘으면 안 되기 때문이다.

**Q2.** PC에서 센 명령어 수를 마이크로컨트롤러의 추정에 그대로 쓰는 것은 얼마나 믿을 만한가?

<details><summary>▶ 답과 설명 보기</summary>

"자릿수"는 믿을 만하고 "정확한 값"은 믿을 수 없다.

- 명령어 집합이 다르다. x86-64 는 명령어 하나가 "메모리에서 읽어서 곱한다"까지 하지만, 단순한 CPU는 읽기와 곱하기가 따로다. 8비트 CPU라면 32비트 덧셈 하나에 명령어 4개가 든다.
- CPI도 명령어마다 다르다. 곱셈과 분기는 더 오래 걸린다.
- 최적화 옵션(-O0, -O1, -O2)에 따라 몇 배씩 달라진다.

그래서 이 추정의 쓸모는 "14 µs 대 1000 µs, 70배 여유가 있다" 또는 "float 는 정수의 약 10배다" 같은 **비교와 자릿수**에 있다. 여유가 2배 이내라면 이 방법으로는 판단할 수 없고, 실제 칩에서 재야 한다 (핀을 켜고 끄며 오실로스코프로 본다).

추정값에는 항상 "어떤 가정으로 구했는가"를 함께 적는다. 숫자만 남으면 나중에 누군가(미래의 나) 그것을 사실로 믿는다.
</details>

**Q3.** 식 "명령어 수 × CPI ÷ 클록 주파수"에서 실행 시간을 줄이는 방법 세 가지와, 각각 누가 정하는지 적어 본다.

<details><summary>▶ 답과 설명 보기</summary>

| 줄이는 것 | 방법 | 누가 |
|---|---|---|
| 명령어 수 | 더 나은 알고리즘(빼고 더하기), 정수 연산, 컴파일러 최적화 | **프로그래머**, 컴파일러 |
| CPI | 파이프라인, 캐시, 더 단순한 명령어 | CPU 설계자 |

펌웨어 개발자가 직접 바꿀 수 있는 것은 첫째 줄이다. 그리고 나머지 둘을 이해하고 있어야 "이 코드가 이 칩에서 도는가"를 미리 판단할 수 있다. 컴퓨터구조를 배우는 이유다.
</details>

**Q1.** 같은 20 ms인데 기준 이득은 멀쩡하고 빠른 이득은 무너진다. 왜인가?

<details><summary>▶ 답과 설명 보기</summary>

"주기가 느리다"는 것은 절대적인 값이 아니라 **제어하려는 움직임에 비해** 느리다는 뜻이다.

닫힌 루프의 시정수 = τm / (1188 × kp):

- 기준 이득: 0.099 / 2.376 = 41.7 ms. 주기 20 ms 면 시정수 동안 두 번은 본다. 아슬아슬하지만 버틴다.
- 빠른 이득: 0.099 / 11.88 = 8.3 ms. 주기 20 ms 면 시정수보다 2.4배 느리다. 제어기가 한 번 보고 다음에 볼 때까지 속도는 이미 갈 데까지 가 있다.

20 ms 동안 듀티는 고정이다. 빠른 이득은 오차에 크게 반응하므로, 20 ms 동안 지나치게 밀어 목표를 넘기고, 다음에는 지나치게 당긴다.

M2의 Q3(오일러 방법의 dt가 크면 발산)과 정확히 같은 구조다. 그때는 계산 방법이 불안정해졌고, 지금은 제어 루프가 불안정해졌다.

경험 법칙: 제어 주기는 닫힌 루프 시정수의 1/10 이하. 거꾸로 말하면 **CPU가 느려서 주기를 짧게 못 하면, 제어를 빠르게 할 수 없다.** 3절의 타이밍 추정이 제어 성능의 한계를 정한다.
</details>

**Q2.** 주기를 0.1 ms 로 더 줄이면 더 좋아질까? 무엇이 문제가 될지 생각해 본다.

<details><summary>▶ 답과 설명 보기</summary>

제어 품질은 1 ms 에서 이미 충분하므로 거의 달라지지 않는다. 대신 비용이 생긴다.

- CPU가 10배 자주 깨어난다. 다른 일(통신, 화면)을 할 시간이 줄고 전력을 더 쓴다.
- float 제어(140 µs)는 주기 100 µs 를 넘는다.
- 정수 적분에서 ki × dt 가 10배 작아진다. q = 8 에서 ki_q = 0.512 → 1 (95 % 오차) 또는 0. 2절의 함정 1이 다시 나온다.

"빠를수록 좋다"가 아니라 "충분히 빠르면 된다". 필요한 만큼만 쓰고 나머지는 여유로 남긴다.
</details>

## 5. 주기를 지키지 못한다 (P8)

지금까지는 `fw_tick()` 이 순식간에 끝난다고 가정했다. 실제로는 계산에 시간이 걸리고, 다른 일(통신, 인터럽트) 때문에 늦어질 수도 있다.

`--exec_us` 옵션은 이렇게 흉내 낸다 (`sim/main.c`):

- 센서는 주기가 시작될 때 읽는다.
- 계산 결과(듀티)는 `exec_us` 뒤에야 PWM에 반영된다.
- 다음 주기가 왔는데 이전 계산이 아직 안 끝났으면, 그 주기는 건너뛴다 (`missed`).
- **펌웨어는 여전히 주기가 1 ms 라고 믿고 있다** (`dt = 0.001`).

```
python run.py P8
```

| 실행 시간 | 실제 실행 / 놓친 주기 (1초) | 1초 때 속도 | 현상 |
|---|---|---|---|
| 0 µs | 1000 / 0 | 400.4 | 기준 |
| 900 µs | 1000 / 0 | 400.4 | 차이 없음 |
| 1,500 µs | 500 / 500 | 398.2 | 느려졌다. 0.6 s 에야 ±2 % 안으로 |
| 5,000 µs | 200 / 800 | 374.9 | 1초가 지나도 6 % 모자란다 |
| 10,000 µs + 빠른 이득 | 100 / 900 | 흔들림 | 자리를 잡지 못한다 |

참고 그래프: `solution/figures/p8_overrun.png`

**Q1.** 900 µs 는 주기의 90 %를 쓰는데도 결과가 거의 같다. 1,500 µs 는 왜 갑자기 나빠지는가?

<details><summary>▶ 답과 설명 보기</summary>

900 µs: 매 주기 계산이 끝난다. 출력이 0.9 ms 늦게 나갈 뿐이고, 이 지연은 시정수 42 ms 에 비해 작다.

1,500 µs: 주기가 왔을 때 이전 계산이 아직 돌고 있다. 한 번 걸러 한 번씩 건너뛴다. 실제로는 2 ms 마다 한 번 실행된다.

그런데 펌웨어는 `dt = 0.001` 로 적분한다. 실제 간격은 0.002 인데 0.001 만큼만 쌓으니, **적분이 절반 속도로 쌓인다.** ki 가 절반이 된 것과 같다. 5,000 µs 에서는 ki 가 1/5 이 된다. 그래서 목표에 도달하는 시간이 길어진다.

즉 문제는 "조금 늦는 것"이 아니라 **"펌웨어가 알고 있는 시간과 실제 시간이 어긋나는 것"** 이다. 주기 안에 끝나기만 하면 괜찮고, 넘는 순간 성질이 달라진다. 이런 경계를 마감 시간(deadline)이라고 한다.
</details>

**Q2.** 이 문제를 고치려면 펌웨어를 어떻게 바꿔야 할까? 생각나는 방법을 적어 보고, 각각 무엇이 필요한지 생각한다.

<details><summary>▶ 답과 설명 보기</summary>

정답이 하나 있는 질문이 아니다. 방향만 적는다.

1. **실제 지난 시간을 재서 dt 로 쓴다.** 타이머 값을 읽는 HAL 함수가 하나 더 필요하다. 적분은 맞아지지만, 늦게 반응하는 것 자체는 그대로다.
2. **놓친 것을 알아차린다.** 놓친 횟수를 세고, 많으면 안전한 상태(모터 정지)로 간다. 감시 타이머(watchdog)가 이런 일을 한다.
3. **계산을 줄인다.** 정수 연산, 더 나은 알고리즘 (3절).
4. **왜 늦는지를 없앤다.** 제어 루프보다 덜 급한 일(통신, 화면)이 CPU를 잡고 있었다면, 제어 루프가 먼저 실행되게 한다. 여러 작업의 우선순위를 정하고, 급한 작업이 덜 급한 작업을 밀어내게 하는 것이 **실시간 운영체제(RTOS)의 스케줄링**이다.

4번은 지금 아는 것으로는 만들 수 없다. 인터럽트, 작업 전환, 두 작업이 같은 변수를 건드릴 때의 문제(경쟁 상태)를 알아야 한다. 계획서에서 "일부러 완전히 해결하지 않는다"고 한 부분이 여기다.
</details>
