# M4. 펌웨어 1판: 비례 제어

**목표**: 센서를 읽고 듀티를 정하는 펌웨어를 만든다. 펌웨어와 바깥 세상의 경계를 이해한다.
**끝났다는 기준**: 목표 속도 근처까지 간다. 남는 오차를 관찰하고 손 계산과 맞춘다.

여기서부터가 프로젝트의 중심이다.

## 1. 읽을 파일 (이 순서로)

1. `firmware/hal.h` — 경계. 함수 두 개의 선언 (20줄)
2. `firmware/firmware.c` — 제어 루프 한 바퀴 `fw_tick()` (70줄)
3. `firmware/controller.c` 의 `clamp_duty`, `control_p` — 계산
4. `sim/main.c` 의 `sensor_read`, `pwm_set` — 경계 건너편의 몸통

## 2. 설명

### 되먹임 제어

M3까지는 듀티를 정해 주고 속도가 얼마가 되든 내버려 두었다 (열린 루프). 이제 속도를 재서 목표와 비교하고 듀티를 고친다 (닫힌 루프).

```
          오차 e              듀티                전압             속도 ω
목표 ──▶(−)──────▶[ 제어기 ]──────▶[ PWM ]──────▶[ 모터 ]────┬────▶
         ▲                                                    │
         └───────────────────[ 센서 ]◀────────────────────────┘
              측정값

      ╰────────── 펌웨어 ──────────╯ ╰────────── 세상 (plant) ──────────╯
```

비례(P) 제어는 가장 단순한 규칙이다: **오차에 비례해서 민다.**

```
듀티 = kp × (목표 − 측정값)
```

### 경계: 함수 두 개

펌웨어는 `plant/` 의 어떤 파일도 include하지 않는다. `motor.w` 라는 변수가 있는지조차 모른다.
바깥과 통하는 길은 `hal.h` 의 두 함수뿐이다.

```c
int  sensor_read(void);     // 속도 센서 값 [rad/s], 정수
void pwm_set(int duty);     // 0 ~ 1000
```

`hal.h` 에는 **선언**만 있다. 몸통은 `sim/main.c` 에 있고, 거기서 가상 모터에 연결된다.

```
firmware/firmware.c          sim/main.c                        plant/
  fw_tick() {                  int sensor_read(void) {
    raw = sensor_read(); ───▶     return sensor_measure(&sensor, motor.w); ──▶ 모터 상태
    ...                        }
    pwm_set(duty);       ───▶  void pwm_set(int duty) {
  }                               pwm.duty = duty / 1000.0;               ──▶ PWM 모델
                               }
```

실제 보드로 옮긴다면 `firmware/` 는 한 글자도 고치지 않고, 두 함수의 몸통만 "ADC 레지스터 읽기", "타이머 비교 레지스터 쓰기"로 바꾼 파일을 대신 링크하면 된다.

이 경계가 주는 것 세 가지:

1. **옮기기 쉽다**: 하드웨어가 바뀌어도 제어 코드는 그대로다.
2. **테스트하기 쉽다**: 보드 없이 PC에서 펌웨어를 돌릴 수 있다. 이 프로젝트 전체가 그 위에 서 있다.
3. **정직하다**: 펌웨어가 `motor.w` (잡음 없는 진짜 속도)를 몰래 볼 수 없다. 실제로는 볼 수 없는 값이니까.

### `fw_tick()` — 루프 한 바퀴

```c
void fw_tick(void)
{
    int raw  = sensor_read();                          // 1. 센서 읽기
    int meas = ma_update(&filt, raw);                  // 2. 잡음 거르기 (지금은 길이 1 = 통과)
    int duty = ctrl.step(&ctrl, target_speed, meas);   // 3. 제어 계산
    pwm_set(duty);                                     // 4. 출력
}
```

실제 보드에서는 타이머가 1 ms마다 인터럽트를 걸어 이 함수를 부른다. 시뮬레이션에서는 `main.c` 가 1000걸음(1 ms)마다 부른다.

`ctrl.step(...)` 은 함수 포인터 호출이다. 지금은 `control_p` 를 가리킨다. [`c_notes.md`](c_notes.md) 6절 참고.

### `static` 전역 변수

`firmware.c` 위쪽의 `static Controller ctrl;` 등은 함수 밖에 있어서 `fw_tick` 이 끝나도 값이 남는다. 펌웨어는 "지난 주기의 값"을 기억해야 하므로(M5의 적분, M7의 필터 버퍼) 이런 상태가 필요하다. `static` 은 "이 파일 안에서만 보인다"는 뜻이다. 다른 파일이 실수로 건드리지 못한다.

### 듀티를 0~1000으로 자르기

kp × 오차는 음수도, 1보다 큰 값도 될 수 있다. 하지만 PWM은 0~100 %만 낼 수 있다. `clamp_duty` 가 범위 밖의 값을 잘라 낸다. 이것을 **포화**라고 한다. (M9의 P6에서 큰 문제를 일으킨다.)

## 4. 생각해 볼 질문

**Q1.** 비례 제어는 왜 목표에 닿지 못하는가? 한 문장으로 설명해 본다.

<details><summary>▶ 답과 설명 보기</summary>

**오차가 0이 되면 듀티도 0이 되어 모터가 멈추기 때문이다.**

400 rad/s로 돌려면 듀티 0.337이 필요하다 (M1 계산 4). 그런데 듀티 = kp × 오차 이므로, 듀티가 0.337이려면 오차가 0.337/kp 만큼 남아 있어야 한다. 시스템은 "오차가 만드는 듀티"와 "그 듀티가 만드는 속도"가 맞아떨어지는 지점에서 멈춘다.

식으로: 최종 속도 ω = 1188 × 듀티 = 1188 × kp × (목표 − ω). K = 1188 × kp 라 두면

```
ω = 목표 × K / (1 + K),     오차 = 목표 / (1 + K)
```

kp = 0.002 → K = 2.376 → ω = 400 × 2.376/3.376 = 281.5. 표와 같다.
</details>

**Q2.** 위 식으로 kp = 0.001, 0.005 일 때의 최종 속도를 직접 계산해 표와 비교한다.

<details><summary>▶ 답과 설명 보기</summary>

- kp = 0.001: K = 1.188 → 400 × 1.188/2.188 = 217.2 (시뮬레이션 217.4)
- kp = 0.005: K = 5.94 → 400 × 5.94/6.94 = 342.4 (시뮬레이션 342.5)

0.1~0.2 정도의 차이는 센서가 정수로 반올림하고(1 rad/s 단위) 듀티가 1/1000 단위이기 때문이다. 연속적인 식으로 푼 손 계산과 디지털로 도는 실제 사이의 틈이다. M8에서 이 틈을 자세히 본다.
</details>

**Q3.** 그러면 kp를 100쯤으로 아주 크게 하면 오차가 거의 0이 되지 않을까? 무엇이 문제일지 예상해 본다.

<details><summary>▶ 답과 설명 보기</summary>

식으로는 맞다. 오차 = 목표/(1 + K) 이니 K가 크면 0에 가까워진다. 하지만 세 가지가 막는다.

1. **센서가 정수다.** 측정값이 1 rad/s 바뀔 때 듀티가 kp만큼 뛴다. kp = 0.3 이면 한 눈금에 듀티가 30 %씩 뛴다.
2. **펌웨어는 1 ms에 한 번만 본다.** 그 사이 듀티는 고정이다. 이득이 크면 1 ms 동안 지나치게 밀어서 목표를 넘고, 다음 주기에 반대로 지나치게 당긴다.
3. **듀티는 0~1로 잘린다.** 결국 0과 1 사이를 오가는 켜고 끄기 제어가 된다.

실험: `build/sim --mode p --kp 0.3 --out out/my_kp03.csv` 를 돌려 듀티를 그려 본다. 속도는 그럴듯해 보이는데 듀티가 0과 1 사이를 미친 듯이 오간다. M5의 P1 실험에서 자세히 다룬다.

이득을 올리는 것이 답이 아니라면, 오차를 없애는 **다른 방법**이 필요하다 → M5의 적분.
</details>

**Q4.** `firmware.c` 는 `sensor_read()` 의 몸통이 없는데 어떻게 컴파일이 되는가? 그리고 `sim/main.c` 를 빼고 컴파일하면 어떤 오류가 나는가?

<details><summary>▶ 답과 설명 보기</summary>

C 프로그램은 두 단계로 만들어진다.

1. **컴파일**: `.c` 파일 하나하나를 따로 기계어(`.o`)로 바꾼다. 이때는 `hal.h` 의 선언만 있으면 된다. "`sensor_read` 라는 함수를 부른다, 주소는 나중에 채운다"는 표시만 남긴다.
2. **링크**: 모든 `.o` 를 합치면서 비워 둔 주소를 채운다. 이때 몸통을 찾지 못하면 오류가 난다.

직접 해 본다: `gcc firmware/*.c` → `undefined reference to 'sensor_read'`, `undefined reference to 'pwm_set'` (그리고 `main` 도 없다고 나온다).

이 오류 메시지가 곧 "펌웨어가 바깥 세상에 요구하는 것의 목록"이다. 두 개뿐이라는 것이 경계가 잘 지켜지고 있다는 증거다.
</details>

**Q5.** 시작 듀티가 kp = 0.002 일 때 0.8, kp = 0.005 일 때 1.0(포화)인 이유는?

<details><summary>▶ 답과 설명 보기</summary>

처음에는 속도가 0이라 오차가 400이다. 듀티 = kp × 400.

- kp = 0.002 → 0.8
- kp = 0.005 → 2.0 → 1.0으로 잘린다

포화된 동안에는 제어기가 무엇을 계산하든 12 V가 그대로 걸린다. 즉 그 구간은 M2의 열린 루프와 똑같이 움직인다. 이 프로젝트의 기준 이득을 kp = 0.002 로 잡은 이유 중 하나가 이것이다. 포화가 없어야 손 계산(선형 식)과 결과가 깔끔하게 맞는다.
</details>
