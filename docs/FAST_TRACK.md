# 빠른 길: 가설 → 실험 → 판정

코드를 읽지 않고 프로젝트 전체를 도는 길. 대략 5~6시간.
먼저 [`ARCHITECTURE.md`](ARCHITECTURE.md) 를 읽는다. 자세히 알고 싶은 단계만 `M*.md` 를 연다.

## 하는 방식

단계마다 네 가지만 한다.

1. **가설**을 한 줄로 적는다 (아래 표의 "먼저 예상").
2. **실행**한다 (명령 한 줄).
3. **그래프**를 본다 (`solution/figures/` 의 참고 그래프).
4. 가설이 **맞았는지** 적는다. 틀렸으면 그 단계 문서의 해당 질문을 읽는다.

기록은 [`../log/EXPERIMENT_TEMPLATE.md`](../log/EXPERIMENT_TEMPLATE.md) 양식으로 남긴다. 예상이 틀린 기록이 가장 쓸모 있다.

준비: `python run.py all` (CSV 생성), 그래프는 이미 `solution/figures/` 에 있다.

## 단계표

| 단계 | 핵심 한 문장 | 먼저 예상 | 볼 그래프 | 확인할 숫자 |
|---|---|---|---|---|
| M2 모터 | 모터는 "빠른 전기 + 느린 기계" 두 시정수로 움직인다 | 12 V 를 걸면 전류는 계속 클까? | `m2_open12` | 속도 1188, 63 % 도달 0.099 s, 전류 11.7 A → 0.12 A |
| M3 PWM | 빠르게 켜고 끄면 인덕터가 평균을 낸다 | 듀티 50 % 와 직류 6 V 는 같을까? | `m3_pwm_vs_dc`, `m3_pwm_zoom` | 속도 차 0.07, 전류 리플 0.3 A |
| M4 P 제어 | 오차에 비례해 밀면 목표에 닿지 못한다 | kp 를 키우면 오차가 0이 될까? | `m4_p_control` | kp 0.002 → 281.5 (오차 29.6 %) |
| M5 PI | 오차를 쌓으면 오차가 0이 된다 | 적분은 부작용이 없을까? | `m5_pi`, `p1_ki` | 399.5, 도달 0.165 s. ki 0.2 → 오버슈트 47 % |
| M5 고유값 | 고유값의 허수부가 출렁임이다 | — | `m5_eigenvalues` | ki 0.2 → 7.4 Hz 예측, 7.2 Hz 관측 |
| P1 kp 과다 | 속도가 멀쩡해도 안은 망가질 수 있다 | kp 0.3 이면 속도가 출렁일까? | `p1_kp` | 듀티 0↔1, 전류 −3.9 ~ 6.9 A |
| M6 검증 | 테스트는 틀린 코드에서 FAIL 해야 테스트다 | 전부 PASS 면 버그가 없나? | — | `python run.py test --solution`, 그리고 M6 문서의 B1~B5 중 하나를 넣어 FAIL 확인 |
| P2 잡음 | 잡음은 kp 배로 듀티에 넘어간다 | 잡음 20 이면 듀티는 얼마나 흔들릴까? (0.002 × 20) | `p2_noise` | 듀티 0.21 ~ 0.46 |
| P3 필터 | 잡음을 줄이면 지연이 생긴다 | N 을 계속 늘리면 계속 좋아질까? | `p3_ma` | N = 64 → 오버슈트 17.7 % |
| P5 정수 | 눈금이 굵으면 사라지고, 그릇이 작으면 넘친다 | q = 4 면 무슨 일이? | `p5_integer` | q 4 → 281.5 (M4 와 같은 값!), 16비트 → 271.8 |
| M8 타이밍 | 명령어 수 × CPI ÷ 클록 < 주기 | float 와 정수는 몇 배 차이? | — | 14 µs 대 140 µs (가정: 16 MHz, CPI 2) |
| P4 주기 | 느린 주기는 "빠른 제어"에서만 문제다 | 20 ms 면 무조건 불안정? | `p4_period` | 기준 이득 멀쩡, 빠른 이득 무너짐 |
| P8 초과 | 주기를 넘는 순간 성질이 바뀐다 | 900 µs 와 1500 µs 의 차이는? | `p8_overrun` | 900 → 차이 없음, 1500 → 절반을 놓침 |
| P6 windup | 못 쓰는 힘이 안에서 쌓인다 | 목표를 낮추면 바로 느려질까? | `p6_windup` | 0.38 s 동안 전속력 유지 |
| P7 켜고 끄기 | 히스테리시스는 횟수와 정밀도를 맞바꾼다 | 띠를 넓히면? | `p7_onoff` | 스위칭 247 → 59 회, 흔들림 30 → 59 |

끝나면 `ARCHITECTURE.md` 의 4절(시계), 5절(맞바꿈), 6절(문제 지도) 표를 다시 본다. 각 줄에 내가 본 그래프가 하나씩 떠올라야 한다.

## 내 역할: 설계하고, 시키고, 판정한다

코드를 직접 쓰지 않는 대신 아래 세 가지는 내가 한다. AI에게 넘기지 않는다.

| 단계 | 내가 하는 것 | AI가 하는 것 |
|---|---|---|
| **설계** | 무엇을 알고 싶은가 (가설), 무엇을 바꾸고 무엇을 잴 것인가, 어떤 결과면 맞고 어떤 결과면 틀린가 (**실행 전에 적는다**) | 설계의 빈틈을 지적한다 |
| **구현** | 부품의 책임과 문(인터페이스)을 정한다 | 코드를 쓴다 |
| **판정** | 결과가 가설과 맞는가, AI의 코드가 내 설계대로인가를 **증거로** 확인한다 | 실행하고 숫자를 낸다 |

AI가 쓴 코드를 믿어도 되는지는 코드를 읽어서가 아니라 **이 세 가지로** 확인한다.

1. **손 계산과 맞는가** (M1의 세 값, M4의 오차 식처럼, 답을 아는 경우를 하나 돌린다)
2. **일부러 틀리게 하면 테스트가 잡는가** (M6의 B1~B5)
3. **경계가 지켜졌는가** (펌웨어가 `plant/` 를 include 하지 않는가: `grep -rn "#include.*plant" firmware/` 가 아무것도 출력하지 않아야 한다)

### AI에게 일을 시킬 때 적는 것 (실험 카드)

```
알고 싶은 것:  (가설 한 줄)
바꿀 것:      (값 하나)
그대로 둘 것:  (나머지 조건)
잴 것:        (어떤 열, 어떤 구간, 어떤 지표)
판정 기준:    (이 값이면 가설이 맞다 / 이 값이면 틀리다)
건드리면 안 되는 것: (예: firmware/ 는 고치지 않는다, hal.h 의 약속은 그대로)
```

예: "가설: 이동평균 지연이 루프 시정수의 절반을 넘으면 오버슈트가 10 % 를 넘는다. 바꿀 것: N = 8, 16, 24, 32, 48, 64. 잴 것: 오버슈트. 판정: 지연 (N−1)/2 ms 가 21 ms 를 넘는 N 부터 10 % 초과면 맞다."

실제로 돌린 결과 (잡음 없이): N = 32 (15.5 ms) 0.4 %, N = 48 (23.5 ms) 9.4 %, N = 64 (31.5 ms) 18.9 %.
판정: **일부만 맞았다.** 21 ms 를 넘는 N = 48 에서 10 % 에 조금 못 미쳤다. "절반"이라는 경계는 대략 맞지만 정확한 값은 아니다. 이렇게 판정 기준을 먼저 적어 두었기 때문에 "대충 맞네"로 넘어가지 않게 된다.

이 카드가 곧 학습 기록이고, 학업계획서의 "문제 → 가설 → 실험 → 결과"의 재료다.

## 그래도 읽어야 하는 최소한

구조를 설계하려면 **약속은 읽을 수 있어야** 한다. 구현은 몰라도 된다.

- 헤더 다섯 개: `firmware/hal.h`, `firmware/firmware.h`, `firmware/controller.h`, `firmware/filter.h`, `plant/motor.h` (합쳐서 150줄, 절반이 주석)
- 각 헤더에서 볼 것: 구조체에 **무엇이 들어 있는가** (= 상태), 함수가 **무엇을 받고 무엇을 돌려주는가** (= 약속)

이것이 안 되면 AI가 구조를 무너뜨려도 알아차릴 수 없다.
