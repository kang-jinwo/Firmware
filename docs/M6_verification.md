# M6. 검증 코드 (내가 직접 쓴다)

**목표**: 사양서의 기준을 자동으로 검사하는 코드를 쓴다. 그리고 그 검사가 진짜로 잡아내는지 확인한다.
**끝났다는 기준**: `python run.py test` 가 전부 PASS. 일부러 틀린 코드를 넣으면 FAIL.

이 단계는 문서를 읽는 시간보다 코드를 쓰는 시간이 길다. 이틀을 잡는다.

## 1. 무엇을 쓰는가

검증은 두 층이다.

| 층 | 묻는 것 | 파일 | 언어 |
|---|---|---|---|
| 단위 테스트 | 함수 하나가 손 계산과 같은 값을 내는가 | `tests/test_filter.c`, `tests/test_controller.c` | C |
| 시스템 테스트 | 전체를 돌린 결과가 사양서 기준을 만족하는가 | `tests/check_spec.py` | Python |

둘 다 필요한 이유: 시스템 테스트가 FAIL이면 "어딘가 틀렸다"는 것만 안다. 단위 테스트가 있으면 "필터는 맞고 제어기가 틀렸다"처럼 범위를 좁힐 수 있다. 반대로 단위 테스트가 전부 PASS여도 함수들을 잘못 이어 붙였으면 전체는 틀린다.

세 파일 모두 뼈대와 예시 하나가 들어 있다. `TODO` 를 채운다.

## 2. `tests/test_filter.c`

필터는 M7에서 쓰지만, 입력과 출력이 단순해서 첫 단위 테스트로 좋다. 먼저 `firmware/filter.c` 를 읽는다 (맨 위 주석에 그림이 있다).

쓰는 순서:

1. 테스트하려는 상황을 정한다. (예: 길이 4에 10, 20, 30, 40, 50)
2. **종이에** 나와야 할 값을 계산한다.
3. 함수를 부르고 `CHECK(나온 값 == 계산한 값);` 을 쓴다.
4. `main` 에서 그 테스트 함수를 부른다.
5. `python run.py test` 로 돌린다.

문법:

```c
MovingAvg f;                  // 구조체 변수 하나
ma_init(&f, 4);               // 길이 4로 초기화. &f = f의 주소
int out = ma_update(&f, 10);  // 값을 넣고 평균을 받는다
CHECK(out == 10);
```

<details><summary>▶ TODO 2의 손 계산 답 (먼저 직접 계산한 뒤에 본다)</summary>

| 넣은 값 | 버퍼 안 | 합 | 나누는 수 | 출력 |
|---|---|---|---|---|
| 10 | 10 | 10 | 1 | 10 |
| 20 | 10 20 | 30 | 2 | 15 |
| 30 | 10 20 30 | 60 | 3 | 20 |
| 40 | 10 20 30 40 | 100 | 4 | 25 |
| 50 | 50 20 30 40 | 140 | 4 | 35 |

다섯 번째에서 가장 오래된 10이 빠지고 50이 들어간다. 여기서 35가 나오면 원형 버퍼가 제대로 도는 것이다. 만약 `f->sum -= f->buf[f->idx];` 줄이 없다면 150/4 = 37이 나온다. 테스트가 잡아내려는 것이 바로 이런 실수다.

정수 나눗셈은 소수점 아래를 버린다는 것도 확인해 두면 좋다 (예: 170/4 = 42).
</details>

## 3. `tests/test_controller.c`

먼저 `firmware/controller.c` 의 `clamp_duty`, `control_p`, `control_pi` 를 다시 읽는다.

문법:

```c
Controller c;
controller_init(&c, 0.002f, 0.02f, 0.001f);   // kp, ki, 제어 주기[s]. 0.002f 의 f = float 상수
int duty = control_pi(&c, 400, 300);          // (제어기, 목표, 측정값) → 듀티 0~1000
```

좋은 테스트를 고르는 요령:

- **경계값**: 문제가 생기는 곳은 대개 경계다. `clamp_duty` 라면 −1, 0, 1000, 1001.
- **손으로 답을 아는 값**: kp × 오차가 딱 떨어지는 숫자.
- **성질**: "어떤 입력에도 듀티는 0~1000" 같은, 값 하나가 아니라 항상 성립해야 하는 것. `for` 문으로 많은 입력을 넣어 확인한다.
- **상태**: 같은 입력을 여러 번 넣었을 때 달라져야 하는 것(적분)과 달라지면 안 되는 것(P 제어).

<details><summary>▶ TODO 4의 손 계산 답: control_pi 에 (목표 400, 측정 300)을 처음 넣으면?</summary>

오차 = 100. 적분 += ki × e × dt = 0.02 × 100 × 0.001 = 0.002.
듀티 = kp × e + 적분 = 0.2 + 0.002 = 0.202 → 정수로 **202**.

두 번째에는 적분이 0.004가 되어 204, 세 번째 206, ... 매 주기 2씩 커진다.
1000번(1초) 뒤에는 0.2 + 2.0 = 2.2 → 1000으로 잘린다.

주의: float 계산은 0.202가 정확히 0.202가 아닐 수 있다 (0.20199999 같은). 코드에 `+ 0.5f` 로 반올림이 들어 있어서 202가 나오지만, float 결과를 `==` 로 비교할 때는 늘 조심한다. 값이 경계(예: 정확히 x.5)에 걸리지 않는 입력을 고르는 것이 안전하다.
</details>

## 4. `tests/check_spec.py`

`run.py test` 는 실험 두 개를 돌린 뒤 이 파일을 부른다.

- `out/spec_nominal.csv`: 기준 이득, 잡음 없음, 1초
- `out/spec_noise.csv`: 잡음 20 rad/s, 이동평균 8개, 1초 (V4용. M7을 하기 전에는 이 항목을 비워 두어도 된다)

쓰는 순서:

1. **`docs/spec.md` 4절의 숫자를 상수로 옮긴다 (TODO 0).** 함수를 쓰기 전에 먼저 한다.
2. 측정 함수를 하나씩 쓴다. 하나 쓸 때마다 `print` 로 값을 찍어 보고, 그래프에서 눈으로 읽은 값과 비교한다.
3. 기준과 비교해 PASS/FAIL을 출력한다.
4. 하나라도 FAIL이면 `sys.exit(1)`.

각 함수를 어떻게 짜는가 (코드가 아니라 방법):

**도달 시간 (TODO 1)**: "±2 % 띠 안에 들어가서 **다시 나오지 않는** 시각." 처음 들어간 시각이 아니다 (출렁이면 들어왔다 나간다).
→ 리스트를 처음부터 끝까지 보면서, 띠 밖에 있는 **마지막** 위치를 기억한다. 그다음 위치의 시각이 답이다. 마지막까지 띠 밖이면 "도달 못 함".

**오버슈트 (TODO 2)**: (속도의 최댓값 − 목표) ÷ 목표. 목표를 넘지 않았으면 0. `max(리스트)` 를 쓴다.

**정상 상태 오차 (TODO 3)**: 마지막 0.2초의 평균과 목표의 차이 ÷ 목표.
→ "t가 (마지막 시각 − 0.2) 이상인 것만 고른다" → 평균 = `sum(리스트) / len(리스트)`.
한 점이 아니라 평균을 쓰는 이유: 마지막 한 점은 우연히 맞거나 틀릴 수 있다.

**흔들림 (TODO 4)**: 마지막 0.5초의 `max − min`.

**듀티 범위 (TODO 6)**: `min(duty) >= 0 and max(duty) <= 1`.

필요한 문법은 [`python_notes.md`](python_notes.md) 2절, 4절.

기대하는 출력 모양 (숫자는 내 코드가 잰 값):

```
PASS  settling time                0.1647 s (limit 0.25 s)
PASS  overshoot                    0.09 % (limit 10 %)
PASS  steady-state error           0.083 % (limit 1 %)
PASS  speed ripple with noise      8.34 rad/s (limit 20 rad/s)
PASS  duty range                   min 0.298, max 0.852 (must stay in 0..1)
```

내 값이 위와 조금 다를 수 있다 (구간을 자르는 방식 차이). 크게 다르면 함수를 다시 본다.

## 5. 테스트를 테스트한다

**전부 PASS가 나온 것은 절반이다.** 항상 PASS만 출력하는 프로그램도 전부 PASS다. 테스트가 쓸모 있으려면 틀린 코드를 넣었을 때 FAIL이 나야 한다.

아래를 하나씩 해 본다. 코드를 한 줄 고치고 → `python run.py test` → 어떤 테스트가 FAIL을 내는지 적고 → `git checkout firmware` 로 되돌린다.

| 번호 | 일부러 넣는 버그 | 어디 |
|---|---|---|
| B1 | `if (duty > PWM_DUTY_MAX) return PWM_DUTY_MAX;` 줄을 주석 처리 | `controller.c` 의 `clamp_duty` |
| B2 | `f->sum -= f->buf[f->idx];` 줄을 주석 처리 | `filter.c` 의 `ma_update` |
| B3 | `float e = (float)(target - measured);` 를 `(measured - target)` 으로 | `controller.c` 의 `control_pi` |
| B4 | `c->integ += add;` 줄을 주석 처리 | `controller.c` 의 `control_pi` |
| B5 | 코드는 그대로 두고 `run.py` 의 `"spec"` 실험에서 `BASE` 대신 `["--kp", "0.002", "--ki", "0.2", "--target", "400"]` | `run.py` |

<details><summary>▶ 정답 테스트(solution)로 돌렸을 때 각각 무엇이 잡는가</summary>

| 버그 | 단위 테스트 | check_spec |
|---|---|---|
| B1 | `test_controller`: 경계값 테스트, 범위 테스트가 FAIL | duty range FAIL (이득이 크거나 포화가 있는 실험일 때) |
| B2 | `test_filter`: 5번째 값이 35가 아니라 37 → FAIL | 잡음 실험의 속도가 틀어져 여러 항목 FAIL |
| B3 | `test_controller`: P가 아닌 PI의 값 테스트가 FAIL | 속도가 0에 머문다 → settling, steady-state FAIL |
| B4 | `test_controller`: "적분이 쌓인다" 테스트 FAIL | steady-state error 29.6 % → FAIL |
| B5 | 전부 PASS (함수는 멀쩡하다) | overshoot 47 % → FAIL |

B5가 중요하다. 코드에 버그가 없어도 **설정값(이득)이 틀리면** 제품은 사양을 못 지킨다. 단위 테스트는 이것을 잡지 못하고 시스템 테스트만 잡는다. 두 층이 다 필요한 이유다.

내 테스트가 어떤 버그를 놓쳤다면, 그것을 잡는 테스트를 하나 더 쓴다. 이 과정(버그를 넣고 → 놓치는지 보고 → 테스트를 보강)이 검증의 핵심이다.
</details>

## 6. 생각해 볼 질문

**Q1.** 도달 시간을 "처음으로 띠 안에 들어간 시각"으로 재면 어떤 잘못된 PASS가 나올 수 있는가?

<details><summary>▶ 답과 설명 보기</summary>

P1의 ki = 2 실험을 생각한다. 속도는 올라가면서 0.03 s쯤에 ±2 % 띠를 지나쳐 695까지 솟고, 그 뒤로 계속 출렁인다. "처음 들어간 시각"으로 재면 0.03 s라는 훌륭한 값이 나와 PASS다. 실제로는 끝까지 자리를 잡지 못했는데도.

측정 함수를 어떻게 정의하느냐가 곧 "무엇을 검증하느냐"다. 사양서에 "들어가 **다시 나오지 않는**"이라고 적어 둔 이유다. 사양의 문장이 모호하면 테스트도 모호해진다.
</details>

**Q2.** 테스트가 전부 PASS면 펌웨어에 버그가 없다고 말할 수 있는가?

<details><summary>▶ 답과 설명 보기</summary>

없다. 말할 수 있는 것은 "**내가 검사한 경우에 대해서는** 사양을 만족한다"까지다.

- 목표 400 rad/s 하나만 검사했다. 1500(낼 수 없는 값)을 주면? → M9의 P6에서 문제가 드러난다.
- 잡음이 없는 경우만 검사했다. → M7
- 제어 주기를 정확히 지킨다고 가정했다. → M8의 P8

테스트는 버그가 **있음**을 보일 수 있지만 **없음**을 증명하지는 못한다. 그래서 "어떤 경우를 검사할지 고르는 것"이 검증에서 가장 어려운 일이고, 경계값과 이상한 입력을 일부러 찾아 넣는다. 5절의 "테스트를 테스트한다"는 내 테스트의 구멍을 찾는 한 가지 방법이다.
</details>

**Q3.** `CHECK` 는 실패해도 프로그램을 멈추지 않고 계속 간다. 첫 실패에서 바로 멈추는 것과 비교해 어떤 점이 좋은가? 나쁜 점은?

<details><summary>▶ 답과 설명 보기</summary>

좋은 점: 한 번 돌려서 실패한 곳을 **전부** 본다. 버그 하나가 여러 테스트를 깨뜨릴 때, 어떤 것들이 함께 깨졌는지가 원인을 찾는 단서가 된다 (예: 범위 테스트만 깨졌다 → `clamp_duty`).

나쁜 점: 앞의 실패 때문에 상태가 망가져서 뒤의 실패가 줄줄이 따라 나올 수 있다. 그때는 **첫 번째 FAIL부터** 본다.

`fail_count` 로 세어 두었다가 마지막에 종료 코드로 돌려주는 구조 덕분에, 사람은 화면의 FAIL 줄을 보고 `run.py` 는 종료 코드를 본다.
</details>
