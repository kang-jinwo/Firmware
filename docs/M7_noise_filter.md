# M7. 센서 잡음과 이동평균 (P2, P3)

**목표**: 잡음이 제어를 어떻게 망가뜨리는지 보고, 이동평균으로 거른다. 필터를 길게 하면 생기는 새 문제를 본다.
**끝났다는 기준**: 학습 기록 2개 (P2, P3).

## 1. 읽을 파일

1. `plant/sensor.c` — 잡음을 만드는 쪽 (세상)
2. `firmware/filter.h`, `firmware/filter.c` — 잡음을 거르는 쪽 (펌웨어)

## 2. 설명

### 센서 모델

실제 센서 값에는 항상 잡음이 섞인다 (전기적 간섭, 진동, 엔코더 눈금 오차). `sensor_measure` 는 진짜 속도에 평균 0, 표준편차 σ 인 난수를 더한 뒤 정수로 반올림한다.

σ = 20 rad/s 이면 측정값은 대부분 진짜 값 ±60 (±3σ) 안에서 흔들린다. 목표 400의 ±15 %다.

`rand()` 대신 직접 만든 난수 발생기를 쓰는 이유: 같은 `--seed` 면 어느 컴퓨터에서나 똑같은 잡음이 나온다. 실험을 되풀이할 수 있어야 "고쳤더니 나아졌다"고 말할 수 있다.

### 이동평균 = 컨볼루션 (4단계: 신호및시스템)

최근 N개의 평균을 낸다.

```
y[n] = ( x[n] + x[n−1] + ... + x[n−N+1] ) / N
```

이것은 임펄스 응답이 h[k] = 1/N (k = 0 ... N−1) 인 시스템과 입력의 컨볼루션이다: y[n] = Σ h[k] · x[n−k].

- **잡음이 줄어드는 이유**: 서로 관계없는 잡음 N개를 평균하면 표준편차가 1/√N 이 된다. N = 8 이면 20 → 7.1.
- **주파수로 보면**: 저역통과 필터다. 느린 변화(진짜 속도)는 통과시키고 빠른 변화(잡음)는 깎는다. 샘플링 1 kHz, N = 8 이면 125 Hz (= 1000/8) 와 그 배수 성분이 완전히 사라진다.
- **대가**: 출력이 늦어진다. 평균은 "최근 N개의 한가운데 시점"의 값에 가깝다. 지연은 (N − 1)/2 샘플이다.

| N | 잡음 (이론) | 지연 |
|---|---|---|
| 1 | 20 | 0 ms |
| 8 | 7.1 | 3.5 ms |
| 32 | 3.5 | 15.5 ms |
| 64 | 2.5 | 31.5 ms |

### 원형 버퍼 (배열과 포인터)

`filter.c` 맨 위의 그림을 본다. 요점은 두 가지다.

1. 값을 한 칸씩 밀지 않는다. 대신 "다음에 쓸 칸" 번호 `idx` 를 옮긴다. 끝에 닿으면 0으로 돌아간다.
2. 매번 N개를 더하지 않는다. 합 `sum` 을 들고 있다가 나가는 값을 빼고 들어오는 값을 더한다. N이 64여도 계산량은 N이 1일 때와 같다. 제어 주기 안에 끝나야 하는 펌웨어에서는 이런 것이 중요하다 (M8).

### 샘플링 주기는 어떻게 정하나

- 닫힌 루프의 시정수가 42 ms다. 그 사이에 충분히 여러 번(10~20번 이상) 보고 고쳐야 연속 제어처럼 동작한다 → 2~4 ms 이하.
- 여유를 두어 1 ms로 정했다. M8의 P4에서 이 여유가 어디까지인지 실험한다.
- 샘플링 정리: 초당 1000번 재면 500 Hz까지만 구별할 수 있다. 그보다 빠른 잡음은 느린 잡음처럼 보인다 (에일리어싱). 디지털 필터로는 걸러 낼 수 없어서, 실제 회로에서는 ADC 앞에 R-C 필터를 둔다.

읽을 점 세 가지:

1. 필터 뒤 잡음은 1/√N 로 준다 (이론 7.1, 3.5, 2.5 와 비슷하다).
2. 듀티와 전류는 확실히 조용해진다.
3. N = 64 에서 오버슈트가 생긴다. **잡음을 줄이려고 넣은 필터가 새 문제를 만들었다.**

## 4. 생각해 볼 질문

**Q1.** 잡음이 있을 때 듀티가 얼마나 흔들릴지 실험 전에 계산할 수 있을까? (힌트: 듀티 = kp × 오차 + 적분)

<details><summary>▶ 답과 설명 보기</summary>

측정값의 잡음은 kp를 곱해 듀티로 그대로 넘어간다. (적분 쪽은 ki × dt = 0.00002 를 곱하므로 무시할 만하다.)

듀티의 표준편차 ≈ kp × σ = 0.002 × 20 = 0.04
범위(±3σ) ≈ 0.337 ± 0.12 → 0.22 ~ 0.46

실험값 0.208 ~ 0.463 과 맞는다. 필터를 넣으면 σ 대신 σ/√N 을 쓴다: N = 8 → 표준편차 0.014.

이 계산에서 알 수 있는 것: **이득 kp가 클수록 잡음에 민감하다.** M5에서 "빠르게 하려면 이득을 올린다"고 했는데, 그 대가가 여기서 나온다. 빠른 응답과 조용한 듀티는 서로 맞바꾸는 관계다.
</details>

**Q2.** N = 64 에서 왜 오버슈트가 생기는가? 숫자로 설명해 본다.

<details><summary>▶ 답과 설명 보기</summary>

N = 64 의 지연은 31.5 ms다. 닫힌 루프의 시정수는 41.7 ms다. 지연이 시정수와 비슷한 크기다.

속도가 올라가는 동안 제어기는 31.5 ms 전의 (더 낮은) 속도를 보고 있다. "아직 멀었다"고 판단해서 계속 세게 민다. 실제 속도는 이미 목표를 넘었는데, 제어기가 그것을 알아차리는 것은 31.5 ms 뒤다. 그래서 넘친다.

샤워기 온도 조절과 같다. 손잡이를 돌리고 물이 바뀌기까지 시간이 걸리면, 뜨겁다 차갑다를 되풀이하게 된다.

N = 32 (지연 15.5 ms)에서는 문제가 없었다. 대략 "지연이 시정수의 절반을 넘으면 위험하다"고 볼 수 있다. 더 빠른 이득(시정수가 더 짧은)에서는 더 짧은 필터에서도 문제가 생긴다. 직접 확인: `build/sim --mode pi --kp 0.005 --ki 0.05 --ma 32 --out out/my.csv` → 오버슈트 29 %.
</details>

**Q3.** 표를 보면 필터를 길게 해도 "실제 속도의 표준편차"는 1.9 → 2.0 으로 줄지 않는다. 필터는 쓸모가 없는 것인가?

<details><summary>▶ 답과 설명 보기</summary>

쓸모는 있다. 다만 **필터가 줄여 주는 것은 듀티와 전류의 요동이고, 속도의 흔들림이 아니다.**

- 빠른 잡음: 필터가 없어도 모터의 관성(시정수 0.1 s짜리 저역통과)이 이미 걸러 준다. 그래서 필터 없이도 속도는 ±수 rad/s만 흔들렸다. 하지만 그 과정에서 듀티와 전류가 요동쳤다 (열, 소음, 마모). 필터는 이것을 없앤다.
- 느린 잡음: 이동평균을 통과하고, 제어기가 "진짜 속도 변화"로 믿고 따라간다. 속도의 흔들림은 주로 여기서 나온다. 이동평균을 길게 해도 이 부분은 그대로다.

즉 "잡음"과 "진짜 신호"가 같은 주파수에 있으면 필터로는 가를 수 없다. 이 프로젝트에서 풀지 못한 채 남는 문제다.

(검증 기준 V4의 "흔들림 ≤ 20 rad/s"는 필터가 없어도 통과한다. 기준을 "속도"로만 잡은 것이 충분했는지 생각해 볼 만하다. 듀티 흔들림에 대한 기준을 추가한다면 어떤 값이 좋을까?)
</details>

**Q4.** `ma_update` 에서 버퍼가 다 차기 전에는 `count` 로 나눈다. 그냥 항상 `len` 으로 나누면 시작할 때 무슨 일이 생길까?

<details><summary>▶ 답과 설명 보기</summary>

버퍼는 0으로 채워져 있다. N = 8 이고 실제 속도가 100이라면 첫 출력은 100/8 = 12.5 다. 제어기는 속도가 실제보다 훨씬 낮다고 보고 필요 이상으로 세게 민다. 8번째 샘플이 들어올 때까지 측정값이 거짓으로 낮다.

`count` 로 나누면 "지금까지 들어온 것만의 평균"이라 처음부터 맞는 값이 나온다.

이런 "시작 직후에만 나타나는 문제"는 테스트에서 놓치기 쉽다. `tests/test_filter.c` 의 TODO 2 (10, 20, 30, 40, 50 → 10, 15, 20, 25, 35)가 바로 이것을 확인한다.
</details>

**Q5.** `filter.h` 에서 버퍼는 `int buf[MA_MAX_LEN];` 로 크기가 고정이다. 필요한 길이만큼만 `malloc` 으로 잡으면 메모리를 아낄 텐데, 왜 그렇게 하지 않았을까?

<details><summary>▶ 답과 설명 보기</summary>

작은 마이크로컨트롤러의 펌웨어에서는 보통 `malloc` 을 쓰지 않는다.

- 메모리가 몇 kB뿐이라, 실행 중에 "메모리가 없다"는 상황이 생기면 대처할 방법이 없다.
- `malloc` 과 `free` 를 되풀이하면 메모리가 조각나고, 걸리는 시간도 일정하지 않다. 제어 주기 안에 끝난다고 보장할 수 없다.

크기를 컴파일할 때 정해 두면 "이 펌웨어는 메모리를 정확히 얼마 쓴다"를 미리 알 수 있다. `ma_init` 이 `len` 을 1 ~ `MA_MAX_LEN` 으로 자르는 것은 배열 밖을 건드리지 않기 위해서다. C는 배열 범위를 검사해 주지 않는다.

메모리를 어떻게 나누고 관리하는지는 시스템프로그래밍과 운영체제에서 본격적으로 배운다.
</details>
