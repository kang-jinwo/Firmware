# 아키텍처 한 장

코드를 한 줄씩 읽지 않고 **구조**로 이 프로젝트를 이해하기 위한 문서.
읽는 순서: 이 문서 → [`FAST_TRACK.md`](FAST_TRACK.md) (실험으로 확인) → [`../advanced/OVERVIEW.md`](../advanced/OVERVIEW.md) (메모리 구조).

코드는 **헤더 파일(`.h`)만** 본다. 헤더는 "이 부품이 밖에 무엇을 약속하는가"이고, `.c` 는 "그 약속을 어떻게 지키는가"다. 아키텍처는 약속의 그림이다.

## 1. 전체 그림

```
                         ┌───────────────── 펌웨어 (firmware/) ─────────────────┐
  목표 속도 ────────────▶│  fw_tick()  : 1 ms 마다 한 바퀴                        │
                         │    ① 읽기 → ② 필터 → ③ 제어 계산 → ④ 출력            │
                         │         (filter)    (controller: P / PI / 정수PI / 켜고끄기) │
                         └──────▲──────────────────────────────────────┬────────┘
                                │ sensor_read()                        │ pwm_set(duty)
                 ═══════════════╪══════════ 경계 (hal.h) ══════════════╪═══════════════
                                │                                      ▼
                         ┌──────┴────────── 세상 (plant/) ─────────────────────┐
                         │  센서 (잡음 + 정수화) ◀── 모터 (전류 i, 속도 ω) ◀── PWM (듀티 → 전압) │
                         └─────────────────────────────────────────────────────┘

  시뮬레이터 (sim/main.c): 시간을 1 µs 씩 전진시키고, 1 ms 마다 fw_tick() 을 부르고, CSV 로 기록한다
  검증 (tests/, solution/): CSV 와 함수를 읽어 사양(docs/spec.md)에 맞는지 PASS/FAIL 로 답한다
```

## 2. 부품과 책임

| 부품 | 책임 (한 문장) | 아는 것 | 모르는 것 | 약속 (헤더) |
|---|---|---|---|---|
| `plant/motor` | 전압을 받아 전류와 속도를 계산한다 | 물리 법칙, 모터 상수 | 제어기가 있다는 사실 | `motor.h` |
| `plant/pwm` | 듀티를 전압 파형으로 바꾼다 | PWM 주기 | 누가 듀티를 정하는지 | `pwm.h` |
| `plant/sensor` | 진짜 속도에 잡음을 섞어 정수로 준다 | 잡음 크기 | 그 값이 어디에 쓰이는지 | `sensor.h` |
| `firmware/filter` | 최근 N개의 평균을 낸다 | 최근 값들 | 그 값이 속도인지 온도인지 | `filter.h` |
| `firmware/controller` | 목표와 측정값으로 듀티를 정한다 | 이득, 적분 값 | 모터의 내부, 하드웨어 | `controller.h` |
| `firmware/firmware` | 위 둘을 순서대로 이어 한 주기를 돈다 | 목표, 순서 | 모터의 진짜 속도 | `firmware.h` |
| `firmware/hal.h` | 펌웨어와 세상 사이의 **유일한 문** | 함수 두 개의 모양 | 문 뒤에 무엇이 있는지 | `hal.h` |
| `sim/main` | 시간을 흘리고, 문 뒤에 가상 모터를 연결한다 | 전부 (유일하게) | — | — |

핵심 원칙: **각 부품은 자기 책임에 필요한 것만 안다.** "모르는 것" 열이 길수록 그 부품은 갈아 끼우기 쉽다.
펌웨어가 모터의 진짜 속도를 모르기 때문에, 문 뒤를 실제 보드로 바꿔도 펌웨어는 그대로다.

## 3. 상태: 무엇이 어디에서 기억되는가

"상태"는 다음 순간에도 남아 있어야 하는 값이다. 버그의 대부분은 상태에서 나온다.

| 상태 | 사는 곳 | 수명 | 바꾸는 쪽 | 잘못되면 |
|---|---|---|---|---|
| 전류 i, 속도 ω | 세상 (`MotorState`) | 내내 | 물리 법칙만 | — |
| 듀티 | 세상 (`Pwm`) | 다음 `pwm_set` 까지 | 펌웨어가 문을 통해 | — |
| 적분 값 | 펌웨어 (`Controller`) | 내내 | 제어 함수만 | 사라지면 오차 29.6 % (M5), 넘치면 폭주 (P5), 쌓이면 늦은 반응 (P6) |
| 최근 N개 측정값 | 펌웨어 (`MovingAvg`) | 내내 | 필터 함수만 | 지연 (P3) |
| 켜짐/꺼짐 | 펌웨어 (`Controller.on`) | 내내 | 켜고 끄기 제어만 | 채터링 (P7) |
| 목표 속도 | 펌웨어 | 내내 | 바깥(사용자) | 실제 보드에서는 경쟁 상태 (심화 A6) |
| 이번 주기의 측정값, 오차 | `fw_tick` 안 | **한 주기** | — | 기억할 필요 없음 |

읽는 법: 펌웨어의 상태는 네 개뿐이다. P1~P8 중 다섯 개가 이 네 개에서 나온다. 설계할 때 "이 시스템의 상태는 무엇이고 어디에 두는가"를 먼저 정하는 이유다. 메모리 구조와의 연결은 [`../advanced/OVERVIEW.md`](../advanced/OVERVIEW.md).

## 4. 시간: 세 개의 시계

```
1 µs    모터 식을 푸는 간격          ████████████████████████████████  (가장 촘촘)
50 µs   PWM 한 주기                  █   █   █   █   █   █   █   █
1 ms    제어 한 주기 (fw_tick)        █                               █
0.5 ms  전기 시정수 (전류가 변하는 빠르기)
42 ms   닫힌 루프 시정수 (속도가 목표를 따라가는 빠르기)
99 ms   기계 시정수 (모터 혼자의 빠르기)
```

설계 규칙 하나로 정리된다: **들여다보는 쪽이 변하는 쪽보다 10배쯤 빨라야 한다.**

| 누가 | 무엇을 | 비율 | 어기면 |
|---|---|---|---|
| 시뮬레이션 1 µs | 전류 0.5 ms | 500배 | 계산이 발산 (M2 Q3) |
| PWM 50 µs | 전류 0.5 ms | 10배 | 전류가 ±6 A 로 출렁임 (M3 Q1, P7) |
| 제어 1 ms | 닫힌 루프 42 ms | 42배 | 불안정 (P4) |
| 계산 시간 14 µs | 제어 1 ms | 70배 | 주기를 놓침 (P8) |

이 표가 M2, M3, P4, P7, P8 을 **같은 문제**로 묶는다.

## 5. 설계 결정과 맞바꿈

아키텍처는 "무엇을 얻으려고 무엇을 내줬는가"의 목록이다.

| 결정 | 얻은 것 | 내준 것 | 확인하는 실험 |
|---|---|---|---|
| 문을 두 함수로 제한 (`hal.h`) | 보드 없이 테스트, 하드웨어 교체가 쉬움 | 펌웨어가 진짜 속도를 못 봄 | M4 |
| 적분 추가 (PI) | 오차 0 | 출렁임, windup 위험 | M5, P1, P6 |
| 이득을 낮게 (kp 0.002) | 포화 없음, 잡음에 둔감, 느린 주기에도 버팀 | 느린 응답 (0.165 s) | P1, P2, P4 |
| 이동평균 N = 8 | 듀티·전류가 조용 | 3.5 ms 지연 | P2, P3 |
| 정수 연산 (q = 8) | 10배 빠름, FPU 불필요 | 반올림 오차, 오버플로 위험 | P5 |
| 필터 버퍼를 고정 크기로 | 메모리 실패 없음, 크기를 미리 앎 | 안 쓰는 칸 낭비 | 심화 A4 |
| 제어 방식을 함수 포인터로 | 방식 교체가 한 줄 | 간접 호출 하나 | M9 |
| 듀티를 펌웨어에서 자름 (clamp) | 범위 밖 값이 하드웨어에 안 감 | — | M6 B1, 심화 A5 |

"내준 것"이 없는 결정은 드물다. 어떤 결정이 좋은지는 **사양(검증 기준)** 이 정한다.

## 6. 문제 지도

P1~P8 이 그림의 어디에서 생기는가.

| 문제 | 어디 | 한 문장 원인 | 구조적 해결 |
|---|---|---|---|
| P1 이득 과다 | ③ 제어 계산 | 지나치게 세게 반응한다 | 이득을 사양에서 역산, 여유를 둔다 |
| P2 잡음 | 센서 → ① | 잡음이 kp 배로 듀티에 넘어간다 | ② 필터 |
| P3 필터 지연 | ② 필터 | 과거를 보고 제어한다 | 지연 ≪ 루프 시정수 |
| P4 느린 주기 | 시계 (1 ms) | 들여다보는 것이 변화보다 느리다 | 4절의 10배 규칙 |
| P5 정수 | ③ 의 숫자 표현 | 눈금이 굵거나(반올림) 그릇이 작다(오버플로) | q 와 자료형을 최댓값에서 역산 |
| P6 windup | ③ 의 적분 상태 + ④ 의 포화 | 못 쓰는 힘을 계속 쌓는다 | 포화 중 적분 정지 |
| P7 켜고 끄기 | ③ + 시계 | 경계에서 계속 뒤집힌다 | 히스테리시스 (상태 하나 추가) |
| P8 주기 초과 | 시계 + 계산 시간 | 펌웨어가 아는 시간과 실제 시간이 어긋난다 | 계산 줄이기, 우선순위 (운영체제) |

## 7. 아키텍처 질문

코드를 보지 않고 답할 수 있어야 한다.

**Q1.** 센서를 엔코더에서 다른 종류로 바꾼다. 어느 부품을 고치고, 어느 부품은 그대로인가?

<details><summary>▶ 답</summary>

문 뒤(`sensor_read` 의 몸통)만 고친다. 단위가 달라지면 그 안에서 rad/s 로 바꿔서 준다. 펌웨어는 그대로다. "문의 약속(정수 rad/s)"만 지키면 된다. 약속 자체를 바꾸면(예: 0.1 rad/s 단위) 펌웨어 전체가 영향을 받는다. 그래서 **인터페이스를 정하는 것이 가장 비싼 결정**이다.
</details>

**Q2.** "목표 속도에 도달하면 LED를 켠다"는 기능을 추가한다. 어디에 넣는가? 문은 몇 개가 되는가?

<details><summary>▶ 답</summary>

판단("도달했는가")은 펌웨어, LED를 켜는 것은 하드웨어다. `hal.h` 에 `led_set(int on)` 을 추가해 문이 세 개가 된다. 판단을 문 뒤(sim)에 넣으면 실제 보드로 옮길 때 그 판단이 사라진다. 기준: **"실제 제품에 들어가야 하는 논리"는 문 앞에.**
</details>

**Q3.** 제어 주기를 1 ms 에서 0.1 ms 로 줄이라는 요구가 왔다. 4절과 5절의 표에서 영향을 받는 줄을 모두 찾는다.

<details><summary>▶ 답</summary>

- 계산 시간 14 µs 대 주기 100 µs: 7배로 여유가 준다. float 였다면 140 µs 로 초과.
- PWM 50 µs 대 제어 100 µs: 제어 한 주기에 PWM 이 두 번뿐이라 듀티가 제대로 반영되지 않는다. PWM 주파수도 올려야 한다.
- 정수 연산: ki × dt 가 10배 작아져 반올림 오차가 커진다 (q 를 올려야 한다 → 오버플로 여유가 준다).
- 이동평균 N = 8 의 지연은 0.35 ms 로 줄어든다 (좋아짐). 같은 잡음 감소를 원하면 그대로.

숫자 하나를 바꾸는데 네 곳이 움직인다. 이 연결을 미리 보는 것이 아키텍처를 본다는 뜻이다.
</details>
