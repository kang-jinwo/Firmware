# 메모리 구조 한 장 (정성적 개요)

코드를 쓰지 않고 **흐름과 구조**로 메모리를 이해하기 위한 문서. 1~2시간.
각 절은 "핵심 한 문장 → 그림 → 실행해서 볼 한 줄 → 설계에 주는 영향" 순서다.
더 깊이 가고 싶은 절만 A1~A6 문서를 연다. 거기의 "직접 해 볼 것"(코드 쓰기)은 선택이다.

## 0. 전체 지도

프로그램이 쓰는 주소 공간은 성격이 다른 다섯 구역이다. 설계자는 **값마다 어느 구역에 둘지**를 정한다.

```
┌──────────────────────┬───────────────┬──────────────────┬────────────────────────────┐
│ 구역                 │ 수명          │ 크기가 정해질 때 │ 펌웨어에서의 쓰임          │
├──────────────────────┼───────────────┼──────────────────┼────────────────────────────┤
│ 레지스터 (하드웨어)  │ 전원 내내     │ 칩이 정함        │ 세상과 닿는 유일한 길      │
│ 스택                 │ 함수 한 번    │ 실행 중          │ 한 주기만 쓰는 임시 값     │
│ 힙                   │ 빌려서 반납까지│ 실행 중          │ 되도록 쓰지 않는다         │
│ data / bss           │ 전원 내내     │ 컴파일할 때      │ 상태 (적분, 필터 버퍼)     │
│ 코드 / 상수 (플래시) │ 전원 꺼져도   │ 컴파일할 때      │ 명령어, 바뀌지 않는 표     │
└──────────────────────┴───────────────┴──────────────────┴────────────────────────────┘
```

세 가지 질문으로 모든 값을 분류한다: **어디에 사는가 / 얼마나 오래 사는가 / 누가 바꿀 수 있는가.**

[`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) 3절의 상태 표가 바로 이 분류다. 아키텍처의 "상태"는 메모리의 "data/bss 에 사는 값"이다.

## 1. 구역은 물리적으로 떨어져 있다 (A1)

**핵심**: 변수의 종류에 따라 완전히 다른 곳에 놓인다. 이름이 어디에 적혀 있는지가 아니라 **수명**이 자리를 정한다.

실행: `python run.py lab a1_memory_map` → 주소의 앞자리가 구역마다 다르다. 같은 함수를 세 번 부르면 지역 변수는 주소가 세 번 다르고, static 변수는 세 번 같다.

**설계에 주는 영향**
- 다음 주기에도 필요한 값은 data/bss, 이번 주기만 쓰는 값은 스택. 이것을 바꾸면 M5의 "적분이 사라지는" 버그가 된다.
- 칩의 RAM은 수 kB다. data/bss + 스택 + 힙이 그 안에 들어가야 한다. **메모리 예산**을 설계할 때 세운다 (타이밍 예산과 짝).
- `const` 는 값을 RAM이 아니라 플래시에 둔다. RAM을 아끼는 설계 수단이다.

## 2. 메모리는 바이트일 뿐, 뜻은 읽는 쪽이 정한다 (A2)

**핵심**: 메모리에는 "이것은 음수다", "이것은 실수다"라는 표시가 없다. 같은 바이트를 다르게 읽으면 다른 값이다.

실행: `python run.py lab a2_bytes` → −2 의 바이트 `fe ff` 를 부호 없이 읽으면 65534. 0x12345678 이 `78 56 34 12` 로 뒤집혀 놓인다.

**설계에 주는 영향**
- 부품 사이, 칩 사이에 값을 넘길 때는 **크기, 부호, 바이트 순서**를 약속에 적어야 한다. 인터페이스 설계의 일부다.
- 자료형의 크기가 곧 담을 수 있는 범위다 (P5의 오버플로). "이 값의 최댓값은 얼마인가"를 설계할 때 따진다.
- 배열 바로 옆에는 다른 값이 있다. 범위를 넘겨 쓰면 옆의 것이 조용히 망가진다. C는 막아 주지 않는다.

## 3. 스택은 빌려 쓰고 바로 돌려주는 자리다 (A3)

**핵심**: 함수가 끝나면 그 자리는 다음 함수가 덮어쓴다. 지워지지 않고 **재사용**된다.

실행: `python run.py lab a3_stack` → 끝난 함수의 변수를 가리키던 포인터가 1234 가 아니라 9999 를 읽는다. 다른 함수가 같은 주소를 썼기 때문이다.

**설계에 주는 영향**
- 함수는 자기 지역 변수의 주소를 밖으로 내보내면 안 된다. 그래서 프로젝트의 모든 `init` 함수는 **호출한 쪽이 가진 자리의 주소를 받아** 채운다. "메모리의 주인은 호출한 쪽"이라는 설계 규칙이다.
- 스택 크기는 작고, 넘쳐도 오류가 없다. 그래서 펌웨어는 재귀와 큰 지역 배열을 금지하고, **가장 깊은 호출 경로**의 사용량을 계산한다.
- 큰 구조체는 복사하지 않고 주소를 넘긴다 (포인터를 쓰는 이유 두 가지 중 하나. 다른 하나는 "원본을 고치려고").

## 4. 힙은 유연하지만 예측할 수 없다 (A4)

**핵심**: 실행 중에 빌리는 메모리는 실패할 수 있고, 걸리는 시간이 일정하지 않고, 오래 쓰면 조각난다.

실행: `python run.py lab a4_heap` → 10바이트를 빌렸는데 간격이 32바이트. 반납한 자리가 곧바로 다른 용도로 다시 쓰인다. 고정 블록 풀은 다섯 번째 요청에 NULL 을 준다.

**설계에 주는 영향**
- 펌웨어는 **"최대 얼마가 필요한가"를 미리 정하고 전부 고정으로 잡는다.** 유연성을 버리고 예측 가능성을 산다. (`MovingAvg` 의 64칸)
- 꼭 빌려야 하면 같은 크기 블록의 풀을 쓴다: 항상 같은 시간, 조각나지 않음.
- "평균적으로 잘 된다"가 아니라 "**최악의 경우에도 된다**"가 기준이다. M8의 타이밍과 같은 사고방식이다.

## 5. 레지스터는 주소가 붙은 하드웨어다 (A5)

**핵심**: 어떤 주소는 메모리가 아니다. 거기에 쓰면 하드웨어가 움직이고, 읽으면 하드웨어의 상태가 나온다.

실행: `python run.py lab a5_registers` → `pwm_set(337)` 은 주소 하나에 337 을 쓰는 것이 전부다. 클램프 없이 −200 을 쓰면 4,294,967,096 이 되어 듀티 100 % 가 된다.

**설계에 주는 영향**
- `hal.h` 의 문 뒤에는 결국 이것이 있다. **펌웨어의 맨 아래층은 "정해진 주소에 정해진 비트를 쓰는 것"** 이다. 계층 구조의 바닥을 안다는 뜻이다.
- 범위 밖의 값이 레지스터에 가면 물리적 사고가 된다. 그래서 **검사는 문 앞(펌웨어)에서** 한다.
- 레지스터 하나에 여러 설정이 비트로 들어 있어, "읽고-고치고-쓰기"를 한다. 이것이 6절의 문제로 이어진다.

## 6. 두 흐름이 같은 값을 건드리면 깨진다 (A6)

**핵심**: `x = x + 1` 은 읽기, 더하기, 쓰기 세 단계다. 그 사이에 다른 흐름(인터럽트, 다른 작업)이 끼어들면 한쪽의 변경이 사라진다.

실행: `python run.py lab a6_race` → 200만 번 더했는데 약 194만. 실행할 때마다 다르다.

**설계에 주는 영향**
- 이 버그는 **테스트로 잡을 수 없다** (가끔만, 재현 안 됨). 설계로 막는다.
- 변수마다 "누가 쓰고 누가 읽는가"를 표로 적는다. 두 흐름이 닿는 변수가 설계의 위험 지점이다.
- 가장 좋은 해결은 **공유하지 않는 구조**다: 한 값은 한 흐름만 쓰게 하고, 주고받을 것은 큐(원형 버퍼)로 넘긴다.
- P8(주기 초과)의 진짜 모습이 이것이다. 여러 작업의 순서와 공유를 다루는 것이 운영체제의 주제다.

## 7. 펌웨어 설계 규칙과 메모리 이유

여섯 절을 한 표로 묶는다. 왼쪽은 흔히 듣는 규칙, 오른쪽은 그 이유다.

| 설계 규칙 | 메모리 쪽 이유 | 절 |
|---|---|---|
| 상태는 구조체에 모으고 static 으로 둔다 | 수명이 "내내"여야 하고, 크기를 컴파일할 때 안다 | 1 |
| 임시 값은 지역 변수로 | 스택은 공짜로 빌리고 자동으로 반납된다 | 1, 3 |
| 구조체는 주소로 넘긴다 | 복사는 스택을 쓰고, 복사본을 고쳐 봐야 원본은 안 바뀐다 | 3 |
| 메모리의 주인은 호출한 쪽 | 함수가 끝나면 그 스택 자리는 재사용된다 | 3 |
| 크기가 분명한 정수형을 쓴다 (`int16_t`, `int32_t`) | 크기가 곧 범위다. 칩마다 `int` 의 크기가 다르다 | 2 |
| 배열에는 항상 최대 길이와 검사가 있다 | 범위를 넘으면 옆의 값이 망가지고 오류는 없다 | 2 |
| malloc 을 쓰지 않는다 | 실패, 불규칙한 시간, 조각남 | 4 |
| 재귀를 쓰지 않는다 | 스택 사용량의 최댓값을 알 수 없다 | 3 |
| 하드웨어에 가는 값은 문 앞에서 자른다 | 레지스터는 범위 밖의 값을 다른 뜻으로 읽는다 | 2, 5 |
| 공유 변수는 함수 뒤에 숨긴다 | 건드리는 곳이 한 군데여야 보호할 수 있다 | 6 |
| 최악의 경우로 예산을 세운다 (시간, 스택, RAM) | 펌웨어는 실패했을 때 물러설 곳이 없다 | 3, 4 |

## 8. AI가 쓴 코드를 구조 수준에서 검토하는 체크리스트

코드를 한 줄씩 읽지 않고, 아래 질문을 AI에게 묻고 **증거를 요구한다.**

1. **상태 목록**: "이 코드에서 주기를 넘어 기억되는 값을 전부 표로 줘. 어디에 살고, 누가 바꾸는지." → 예상보다 많으면 구조가 복잡해진 것이다.
2. **경계**: "펌웨어가 `hal.h` 말고 바깥의 무엇을 include 하는가?" → `grep` 결과로 확인.
3. **범위**: "각 정수 변수의 최댓값과 자료형의 한계를 표로 줘." → 여유가 2배 이하인 줄이 위험 지점.
4. **동적 메모리와 재귀**: "malloc, 재귀, 큰 지역 배열이 있는가?" → `grep` 결과로 확인.
5. **스택과 시간 예산**: "가장 깊은 호출 경로와 그때의 스택 사용량, 한 주기의 명령어 수는?" → `-fstack-usage`, `objdump` 결과로 확인.
6. **공유**: "실제 보드에서 인터럽트와 메인 루프가 함께 건드리는 변수는?" → 표로.
7. **검증**: "이 변경이 틀렸다면 어느 테스트가 FAIL 하는가? 실제로 틀리게 해서 보여 줘."

각 답은 "그렇습니다"가 아니라 **명령의 출력**으로 받는다. AI에게 일을 맡길 때 설계자가 쥐고 있어야 하는 것은 이 질문들이다.
