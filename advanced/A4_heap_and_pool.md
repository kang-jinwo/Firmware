# A4. 힙과 고정 블록 풀

실습: `python run.py lab a4_heap` (코드: `advanced/labs/a4_heap.c`)

스택은 "함수가 끝나면 사라진다", data/bss 는 "크기가 컴파일할 때 정해진다". 둘 다 안 맞을 때, 즉 **실행 중에 크기가 정해지고 함수보다 오래 살아야 하는** 메모리가 필요할 때 힙을 쓴다.

## 1. 먼저 예상한다

1. `malloc(10)` 을 두 번 부르면 두 주소의 간격은 10바이트일까?
2. `free(a)` 한 직후에 `malloc(10)` 을 다시 부르면 어떤 주소가 올까?
3. 4칸짜리 풀에서 다섯 번째로 빌리려 하면 무엇이 돌아올까?

## 2. 실행 결과 (예)

```
[1] malloc: 요청한 크기와 실제 간격
  a = 0x5577c7fc42b0
  b = 0x5577c7fc42d0   (a 와의 간격 32 바이트: 10을 달라 했는데?)
  c = 0x5577c7fc42f0
[2] free 한 자리는 다시 쓰인다
  다시 malloc(10) = 0x5577c7fc42b0
[3] 고정 블록 풀: 주소가 미리 정해져 있다
  alloc #0 -> 0x55779b1dc040   (used = 1)
  alloc #1 -> 0x55779b1dc060   (used = 2)
  alloc #2 -> 0x55779b1dc080   (used = 3)
  alloc #3 -> 0x55779b1dc0a0   (used = 4)
  alloc #4 -> (nil)   (used = 4)
  blk[1] 을 돌려준 뒤 alloc -> 0x55779b1dc060  (같은 자리)
```

## 3. 설명

### malloc 은 장부를 쓴다

10바이트를 달라고 했는데 간격이 32바이트다. `malloc` 은 블록마다 "이 블록은 몇 바이트다"라는 머리말(헤더)을 앞에 붙이고, 정렬을 위해 크기를 올림한다. `free(a)` 가 크기를 묻지 않고도 얼마를 돌려받는지 아는 이유다.

```
        ┌────────┬──────────────────────┐┌────────┬──────────────────────┐
        │ 헤더   │ 내가 쓰는 곳 (a)     ││ 헤더   │ 내가 쓰는 곳 (b)     │
        └────────┴──────────────────────┘└────────┴──────────────────────┘
                 ↑ malloc 이 돌려준 주소
```

### 힙에서 생기는 버그

| 이름 | 무엇 | 증상 |
|---|---|---|
| 누수 (leak) | `malloc` 하고 `free` 를 안 한다 | 메모리가 조금씩 줄다가 며칠 뒤 `malloc` 이 실패 |
| 해제 후 사용 (use-after-free) | `free` 한 포인터로 계속 읽고 쓴다 | [2]처럼 그 자리가 다른 용도로 다시 쓰여서, 남의 데이터를 망가뜨린다 |
| 이중 해제 (double free) | 같은 것을 두 번 `free` | 장부가 깨져 한참 뒤 엉뚱한 곳에서 죽는다 |
| 넘침 | 빌린 크기보다 더 쓴다 | 옆 블록의 헤더를 덮어 장부가 깨진다 |
| 조각남 (fragmentation) | 크고 작은 블록을 빌리고 돌려주기를 되풀이 | 빈 곳의 합은 충분한데 **이어진** 큰 자리가 없어 실패 |

해제 후 사용은 A3의 dangling pointer 와 같은 병이다. "가리키던 것의 수명이 끝났는데 포인터는 남아 있다."

### 펌웨어가 malloc 을 피하는 이유

1. **실패했을 때 할 수 있는 일이 없다.** PC 프로그램은 오류를 내고 끝나면 되지만, 모터를 돌리던 펌웨어는 끝날 수 없다.
2. **걸리는 시간이 일정하지 않다.** 빈 자리를 찾아 장부를 뒤지는 시간이 그때그때 다르다. 제어 주기 안에 끝난다고 보장할 수 없다 (M8).
3. **조각남은 시간이 지나야 나타난다.** 한 달 켜 두어야 재현되는 버그는 테스트로 잡기 어렵다.
4. **RAM이 작다.** 헤더가 블록마다 8~16바이트씩 든다.

그래서 펌웨어는 필요한 메모리를 **전부 static 으로** 잡는다. 프로젝트의 `static MovingAvg filt;` 와 `int buf[MA_MAX_LEN];` 이 그 방식이다. "최대 얼마까지 필요한가"를 설계할 때 정한다.

### 그래도 빌리고 돌려줘야 할 때: 고정 블록 풀

통신 메시지처럼 개수가 그때그때 달라지는 것은 **같은 크기의 블록 N개**를 static 으로 잡아 두고 빌려준다.

```
storage (static, bss)
┌──────────┬──────────┬──────────┬──────────┐
│ 블록 0   │ 블록 1   │ 블록 2   │ 블록 3   │
└──────────┴──────────┴──────────┴──────────┘

빈 블록끼리는, 빈 블록의 첫 칸에 "다음 빈 블록의 주소"를 적어 잇는다.

free_list ──▶ [블록 0: 다음=블록 1] ──▶ [블록 1: 다음=블록 2] ──▶ [블록 2: 다음=블록 3] ──▶ [블록 3: 다음=NULL]
```

- 빌리기: `free_list` 가 가리키는 블록을 주고, `free_list` 를 그 블록에 적혀 있던 "다음"으로 옮긴다.
- 돌려주기: 그 블록 첫 칸에 지금의 `free_list` 를 적고, `free_list` 가 그 블록을 가리키게 한다.

둘 다 대입 두세 번이다. **항상 같은 시간**이 걸리고, 블록 크기가 같으므로 **조각나지 않는다.** 별도의 장부도 없다 (빈 블록 자체를 장부로 쓴다).

`*(void **)block = p->free_list;` 읽는 법: `block` 은 블록의 주소. `(void **)block` 은 "이 자리에 주소(`void *`)가 하나 들어 있다고 보겠다". 앞의 `*` 로 그 자리에 쓴다. 즉 **블록의 첫 8바이트에 주소를 적는다.** 프로젝트에서는 나오지 않았던, 이중 포인터가 실제로 필요한 곳이다.

## 4. 프로젝트와 연결

- `MovingAvg` 의 `buf[MA_MAX_LEN]`: 실제로는 8칸만 써도 64칸을 잡는다. 메모리를 낭비하는 대신 실패할 일이 없고 크기를 미리 안다. (M7 Q5)
- `ma_init`, `controller_init` 이 구조체를 돌려주지 않고 주소를 받는 것(A3 Q1)도 같은 원칙이다. 메모리를 누가 언제 잡는지를 호출한 쪽이 정한다.
- 세 질문으로 보면: 힙은 "얼마나 오래 사는가"를 **프로그래머가 직접 책임지는** 구역이다. 스택은 컴파일러가, bss 는 처음부터 끝까지로 정해져 있다.

## 5. 질문

**Q1.** 풀이 꽉 찼을 때 `pool_alloc` 은 `NULL` 을 돌려준다. 호출한 쪽이 확인하지 않고 그 포인터에 쓰면 어떻게 되는가? PC와 마이크로컨트롤러에서 각각.

<details><summary>▶ 답과 설명 보기</summary>

`NULL` 은 주소 0이다.

- PC: 운영체제가 주소 0 근처를 접근 금지로 해 두었다. 즉시 죽는다 (Segmentation fault). 죽는 것이 다행이다. 어디서 틀렸는지 바로 안다.
- 마이크로컨트롤러: 주소 0은 **진짜로 있는 메모리**인 경우가 많다 (보통 인터럽트 벡터 테이블이 있는 곳). 쓰기가 무시되거나, 최악에는 중요한 표가 망가진다. 죽지 않고 계속 돈다.

그래서 펌웨어에서는 "실패할 수 있는 함수의 반환값은 반드시 확인한다"가 규칙이다. `sim/main.c` 의 `if (fp == NULL)` 이 같은 습관이다.
</details>

**Q2.** 같은 블록을 두 번 `pool_free` 하면 빈 목록이 어떻게 되는가? 그림으로 그려 본다.

<details><summary>▶ 답과 설명 보기</summary>

블록 A를 돌려준다: `free_list → A → (이전 목록)`.
A를 한 번 더 돌려준다: A의 첫 칸에 지금의 `free_list`(= A 자신)를 적는다. `free_list → A → A → A → ...`

A가 자기 자신을 가리키는 고리가 된다. 이후 `pool_alloc` 은 **영원히 A만** 돌려준다. 서로 다른 두 곳이 같은 블록을 받아 서로의 데이터를 덮어쓴다. 그리고 `used` 는 음수가 된다.

막는 방법: 블록마다 "빌려준 상태인가" 표시를 두고 `pool_free` 에서 확인한다. 직접 해 볼 것에 있다.
</details>

**Q3.** 블록 크기가 32바이트인 풀에서 40바이트가 필요하면 어떻게 하나? 고정 블록 풀의 단점은 무엇인가?

<details><summary>▶ 답과 설명 보기</summary>

빌릴 수 없다. 고정 블록 풀은 **유연성을 버리고 예측 가능성을 얻은** 것이다.

- 필요한 것보다 작은 요청에도 한 블록(32바이트)을 통째로 쓴다 (내부 낭비).
- 큰 것은 못 빌린다.

실제로는 크기별로 풀을 여러 개 둔다 (16바이트 풀, 64바이트 풀, 256바이트 풀). 각 풀의 블록 수는 "최악의 경우 동시에 몇 개가 필요한가"를 따져서 정한다. 이 "최악의 경우를 미리 센다"는 것이 M8의 타이밍, A3의 스택과 같은 펌웨어의 사고방식이다.
</details>

## 6. 직접 해 볼 것

- [ ] `a4_heap.c` 의 풀 부분을 `advanced/my/pool.c` 로 복사하고, **보지 않고 다시 쓴다.** `pool_init`, `pool_alloc`, `pool_free` 세 함수. 막히면 그림을 다시 그린다.
- [ ] 이중 해제를 잡는다: 블록 수만큼의 `uint8_t in_use[BLOCK_COUNT]` 배열을 `Pool` 에 추가하고, `pool_free` 가 이미 빈 블록이면 아무것도 하지 않고 오류 값을 돌려주게 한다. 블록 주소에서 번호를 구하는 식을 생각해 본다 (포인터 뺄셈, A2).
- [ ] 풀에 대한 단위 테스트를 M6의 `CHECK` 로 쓴다: 전부 빌리면 NULL, 돌려주면 다시 빌려짐, 이중 해제가 막힘, 풀 밖의 주소를 돌려주면 막힘.
- [ ] (선택) `gcc -fsanitize=address -g` 로 `malloc` 한 것을 `free` 한 뒤 읽는 프로그램을 돌려 오류 메시지를 읽는다.
