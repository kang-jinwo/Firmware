# A3. 스택: 함수 호출의 메모리

실습: `python run.py lab a3_stack` (코드: `advanced/labs/a3_stack.c`)

이 실습의 [2]와 [3]은 **일부러 해서는 안 되는 일**을 한다. 무슨 일이 생기는지 눈으로 보기 위해서다.

## 1. 먼저 예상한다

1. 함수를 더 깊이 부를수록 지역 변수의 주소는 커질까, 작아질까?
2. `make_local` 은 자기 지역 변수 `secret` 의 주소를 전역 포인터에 넣고 끝난다. 그 뒤에 그 포인터로 값을 읽으면 1234 가 나올까?
3. 8칸짜리 `char name[8]` 에 10글자를 복사하면 넘친 2글자는 어디로 갈까?

## 2. 실행 결과 (예)

```
[1] 호출이 깊어질수록 주소가 어느 쪽으로 가나
  depth(1)  &marker = 0x7ffcde30d414
  depth(2)  &marker = 0x7ffcde30d3e4
  depth(3)  &marker = 0x7ffcde30d3b4
  depth(4)  &marker = 0x7ffcde30d384
[2] 사라진 지역 변수를 가리키는 포인터 (dangling pointer)
  make_local 안:      &secret = 0x7ffcde30d414, *g_dangling = 1234
  overwrite_stack 안: &other = 0x7ffcde30d414
  두 함수가 끝난 뒤:  *g_dangling = 9999   (1234 가 아니면 다른 함수가 그 자리를 덮어쓴 것이다)
[3] 버퍼를 넘겨 쓰면 옆 변수가 망가진다
  전: checksum = 0xAABBCCDD
  후: checksum = 0xAABB4A49   ('I' = 0x49, 'J' = 0x4A)
[4] 재귀 한 번에 스택을 얼마나 쓰나
  recurse_sum(100) = 5050  (깊이 100 → 스택 약 100 kB 사용)
```

## 3. 설명

### 스택 프레임

함수를 부를 때마다 스택에 그 함수 몫의 구역(프레임)이 하나 쌓인다. 함수가 끝나면 그 구역을 통째로 반납한다.

```
높은 주소
┌─────────────────────┐
│ main 의 프레임      │  지역 변수들
├─────────────────────┤
│ depth(1) 의 프레임  │  돌아갈 주소, marker, ...
├─────────────────────┤
│ depth(2) 의 프레임  │
├─────────────────────┤
│ depth(3) 의 프레임  │
├─────────────────────┤  ← 스택 포인터 (지금 꼭대기)
│ (아직 안 쓴 곳)     │
낮은 주소
```

프레임 하나에 들어가는 것: 지역 변수, 일부 인자, **돌아갈 주소**(이 함수가 끝나면 어느 명령어로 돌아갈지), 저장해 둔 CPU 레지스터 값.

"쌓는다 / 반납한다"는 스택 포인터라는 CPU 레지스터 하나의 값을 빼고 더하는 것이 전부다. 그래서 지역 변수는 만드는 비용이 거의 없다. 대신 **반납한 자리는 지워지지 않고, 다음 함수가 그대로 덮어쓴다.**

### [2] 사라진 변수를 가리키는 포인터

`make_local` 이 끝나면 `secret` 이 있던 자리(0x...d414)는 반납된다. 다음에 불린 `overwrite_stack` 의 지역 변수 `other` 가 **정확히 같은 주소**에 놓이고 9999 를 쓴다. 전역 포인터는 여전히 그 주소를 들고 있으므로 9999 를 읽는다.

이 버그가 무서운 이유:

- 컴파일이 된다 (경고조차 안 나오게 쓸 수 있다).
- **우연히 동작할 때가 많다.** 사이에 다른 함수를 부르지 않으면 1234 가 그대로 남아 있다. 코드를 조금 고쳤더니 갑자기 값이 이상해진다.
- 최적화 옵션을 바꾸면 증상이 달라진다.

규칙: **지역 변수의 주소를 그 함수보다 오래 사는 곳(전역, 반환값, 구조체)에 넣지 않는다.**

### [3] 버퍼 넘침

`name[8]` 다음 자리에는 `checksum` 이 있다. 10글자를 복사하면 9번째, 10번째 글자('I', 'J')가 `checksum` 의 낮은 2바이트를 덮는다. 0xAABBCCDD → 0xAABB4A49. 리틀 엔디안이라 낮은 주소에 낮은 자리(DD, CC)가 있었고 그것이 49, 4A 로 바뀌었다 (A2).

스택의 지역 배열에서 같은 일이 생기면 옆에 있는 것은 **돌아갈 주소**일 수 있다. 그것이 덮이면 함수가 끝날 때 엉뚱한 곳으로 점프한다. 이것이 버퍼 오버플로 공격의 원리이고, 펌웨어가 이유 없이 리셋되는 흔한 원인이다.

### [4] 스택의 크기

PC의 스택은 보통 8 MB라서 신경 쓰지 않는다. 마이크로컨트롤러는 RAM 전체가 수 kB이고, 그중 스택 몫은 수백 바이트 ~ 수 kB다. 스택이 넘치면(stack overflow) 아래쪽에 있는 bss/data 의 전역 변수를 덮어쓴다. 오류 메시지는 없다. 전역 변수의 값이 어느 순간 바뀌어 있을 뿐이다.

그래서 펌웨어에서는:

- **재귀를 쓰지 않는다** (깊이를 미리 알 수 없다).
- **큰 배열을 지역 변수로 두지 않는다** (`char buf[1024];` 를 함수 안에 쓰지 않는다. static 으로 둔다).
- 호출 깊이와 각 함수의 프레임 크기를 더해 **최악의 스택 사용량**을 계산한다.

## 4. 프로젝트와 연결

- **M2 Q2 (값으로 넘기면 모터가 안 돈다)**: `motor_step(MotorState m, ...)` 이면 호출할 때 `motor` 16바이트가 `motor_step` 의 프레임에 **복사**된다. 함수는 복사본을 고치고, 프레임이 반납되면 복사본도 사라진다. 포인터로 넘기면 복사되는 것은 주소 8바이트이고, 그 주소는 bss 에 있는 진짜 `motor` 를 가리킨다.
- **`fw_tick` 의 호출 사슬**: `fw_tick → ma_update`, `fw_tick → control_pi_int → clamp_duty`. 가장 깊을 때 프레임이 3개다. 재귀가 없으므로 최악의 스택 사용량을 계산할 수 있다.
- **`MovingAvg` 를 포인터로 넘기는 이유**: 값으로 넘기면 호출마다 280바이트를 스택에 복사한다. 느리고, 작은 칩에서는 스택이 넘칠 수 있다.

## 5. 질문

**Q1.** 아래 함수는 무엇이 문제인가? 어떻게 고칠 수 있는가? (두 가지 이상)

```c
char *make_name(int id)
{
    char buf[16];
    sprintf(buf, "motor%d", id);
    return buf;
}
```

<details><summary>▶ 답과 설명 보기</summary>

`buf` 는 `make_name` 의 프레임에 있다. 함수가 끝나면 반납되므로 돌려준 주소는 [2]와 같은 dangling pointer 다. (gcc 는 이 경우 경고를 준다: `function returns address of local variable`.)

고치는 방법:

1. **호출한 쪽이 자리를 마련하고 주소를 넘긴다** (펌웨어에서 가장 흔한 방법):
   ```c
   void make_name(char *out, size_t size, int id) { snprintf(out, size, "motor%d", id); }
   char name[16];  make_name(name, sizeof name, 3);
   ```
   자리의 수명을 호출한 쪽이 책임진다. 크기도 함께 넘겨 넘침을 막는다.
2. `static char buf[16];` 으로 바꾼다. bss 에 살므로 사라지지 않는다. 단, 두 번 부르면 앞의 결과가 덮인다.
3. `malloc` 으로 힙에 잡아 돌려준다. 받는 쪽이 `free` 해야 한다 (A4).

프로젝트의 `ma_init(&f, len)`, `controller_init(&c, ...)` 이 1번 방식이다. 구조체를 만들어 돌려주지 않고, **호출한 쪽이 가진 구조체의 주소를 받아 채운다.**
</details>

**Q2.** `fw_tick` 이 도는 중에 스택이 가장 깊어지는 순간의 사용량을 어림하려면 무엇을 알아야 하는가?

<details><summary>▶ 답과 설명 보기</summary>

1. **호출 사슬**: 가장 깊은 경로 (`fw_tick → control_pi_int → clamp_duty`).
2. **각 함수의 프레임 크기**: 지역 변수 + 돌아갈 주소 + 저장하는 레지스터. gcc 의 `-fstack-usage` 옵션을 주면 함수별 크기를 `.su` 파일로 써 준다.
3. **인터럽트**: 실제 칩에서는 어느 순간에든 인터럽트가 끼어들어 그 처리 함수의 프레임이 **같은 스택 위에** 쌓인다. 최악은 "가장 깊은 순간에 인터럽트가 걸렸을 때"다.

직접 해 본다: `gcc -std=c99 -O1 -fstack-usage -c firmware/controller.c -o build/controller.o` → `build/controller.su` 를 연다.

이 합이 칩의 스택 크기보다 작다는 것을 보이는 것이 M8의 타이밍 추정과 짝이 되는 **메모리 추정**이다. 시간(주기 안에 끝나는가)과 공간(스택 안에 들어가는가) 둘 다 미리 따진다.
</details>

**Q3.** [2]에서 사이에 `overwrite_stack()` 호출을 지우면 1234 가 그대로 나온다. 그러면 "동작하는 코드"인가?

<details><summary>▶ 답과 설명 보기</summary>

아니다. 반납한 자리를 아직 아무도 안 썼을 뿐이다. `printf` 를 한 줄 넣거나, 컴파일러를 바꾸거나, 인터럽트가 그 순간에 걸리면 값이 바뀐다.

C 표준은 이런 것을 **정의되지 않은 동작**이라고 한다. "무슨 일이 생겨도 컴파일러의 잘못이 아니다"라는 뜻이다. 테스트를 통과했다고 해서 맞는 코드가 아닌 가장 대표적인 경우이고, M6의 "테스트는 버그가 없음을 증명하지 못한다"의 가장 날카로운 예다.

찾는 도구: `gcc -fsanitize=address -g` 로 컴파일하면 실행 중에 이런 접근을 잡아 준다. 실습 파일에 직접 써 본다:
`gcc -std=c11 -O0 -g -fsanitize=address -o build/a3_asan advanced/labs/a3_stack.c && build/a3_asan`
</details>
