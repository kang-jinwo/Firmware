# A5. 레지스터와 비트 조작

실습: `python run.py lab a5_registers` (코드: `advanced/labs/a5_registers.c`)

지금까지 본 메모리는 "값을 넣으면 그 값이 남아 있는 곳"이었다. 마이크로컨트롤러에는 **주소는 있지만 메모리가 아닌 곳**이 있다. 그 주소에 값을 쓰면 하드웨어가 움직이고, 읽으면 하드웨어의 상태가 나온다. 이것을 레지스터라고 하고, 펌웨어가 세상과 닿는 유일한 길이다.

프로젝트의 `sensor_read()` 와 `pwm_set()` 의 "진짜 몸통"이 어떻게 생겼는지 보는 장이다.

## 1. 먼저 예상한다

1. 구조체에 `uint32_t` 멤버 네 개가 있다. 두 번째 멤버의 주소는 구조체 주소 + 얼마인가?
2. `CR` 이 0일 때 `CR |= (1u << 3);` 뒤의 값은? 이어서 `CR |= (1u << 0);` 뒤는?
3. `CR &= ~(1u << 0);` 은 무엇을 하는가?
4. `pwm_set(-200)` 으로 −200 이 `uint32_t` 레지스터에 들어가면 얼마가 되는가?

## 2. 실행 결과 (예)

```
[1] 구조체 멤버의 주소 = 레지스터의 주소
  TIM1       = 0x564da77fb020
  &TIM1->CR  = 0x564da77fb020
  &TIM1->ARR = 0x564da77fb024
  &TIM1->CCR = 0x564da77fb028
[2] 비트 조작
  CR 처음 = 0x00000000  ...0000 0000 0000 (아래 12비트)
  CR 설정 = 0x00000509  ...0101 0000 1001 (아래 12비트)
  켜져 있나? yes
  분주비 칸 = 5
  CR 끔   = 0x00000508  ...0101 0000 1000 (아래 12비트)
[3] HAL 두 함수
  pwm_set(337) 뒤 CCR = 337
  sensor_read() = 398
[4] 클램프가 없으면: pwm_set(-200)
  CCR = 4294967096  (부호 없는 32비트로 바뀌었다)
```

## 3. 설명

### 메모리 맵 입출력

칩 설명서(데이터시트)에는 이런 표가 있다.

```
타이머 1, 시작 주소 0x40012C00
  +0x00  CR   제어
  +0x04  ARR  주기
  +0x08  CCR  비교 값 (듀티)
  +0x0C  SR   상태
```

C에서는 이 표를 **구조체로 옮기고, 숫자 주소를 구조체 포인터로 바꿔** 쓴다.

```c
typedef struct { volatile uint32_t CR, ARR, CCR, SR; } TimerRegs;
#define TIM1 ((TimerRegs *)0x40012C00)

TIM1->CCR = 337;      /* 주소 0x40012C08 에 337 을 쓴다 → PWM 듀티가 바뀐다 */
```

구조체 멤버의 순서가 곧 주소의 순서다 (A2의 오프셋). `->` 는 "시작 주소 + 오프셋"을 계산해 주는 문법일 뿐이다. 포인터와 구조체를 왜 배웠는지가 여기서 드러난다.

PC에서는 주소 0x40012C00 에 아무것도 없으므로, 실습은 전역 변수 하나를 가짜 칩으로 삼는다. `#define TIM1 (&fake_timer)`. 그 아래 코드는 실제 펌웨어와 글자 하나 다르지 않다.

### volatile

컴파일러는 "이 변수는 내가 쓴 뒤로 아무도 안 바꿨으니 다시 읽을 필요 없다"고 보고 읽기를 생략한다. 일반 메모리에서는 맞는 최적화다.

레지스터는 **하드웨어가 바꾼다.** `while (ADC1->SR == 0) { }` (변환이 끝나기를 기다린다)에서 컴파일러가 `SR` 을 한 번만 읽고 "0이었으니 영원히 0"이라고 판단하면 무한 루프가 된다. `volatile` 은 "이 값은 내가 모르는 사이에 바뀔 수 있다. 쓸 때마다 진짜로 읽고, 쓰라고 한 것은 전부 진짜로 써라"라는 뜻이다.

### 비트 조작 네 가지

레지스터 하나에 설정 여러 개가 비트 단위로 들어 있다. 다른 비트를 건드리지 않고 원하는 비트만 바꿔야 한다.

| 하려는 일 | 코드 | 원리 |
|---|---|---|
| 비트 켜기 | `reg \|= (1u << n);` | OR: 1과 OR 하면 1, 0과 OR 하면 그대로 |
| 비트 끄기 | `reg &= ~(1u << n);` | AND: 0과 AND 하면 0, 1과 AND 하면 그대로. `~` 는 모든 비트를 뒤집는다 |
| 비트 확인 | `if (reg & (1u << n))` | 그 비트만 남기고 나머지를 0으로 |
| 여러 비트짜리 칸 바꾸기 | `reg = (reg & ~MASK) \| (value << POS);` | 그 칸을 먼저 지우고, 새 값을 넣는다 |

예: `CR` 이 `0000 0000 1000` 일 때 분주비 칸(8~10번 비트)에 5 (`101`) 넣기.

```
MASK        = 0111 0000 0000
~MASK       = 1000 1111 1111
CR & ~MASK  = 0000 0000 1000     (칸을 지움. 3번 비트는 그대로)
5 << 8      = 0101 0000 0000
OR          = 0101 0000 1000
```

`1u` 의 `u` 는 unsigned. 부호 있는 수를 31번 밀면 부호 비트를 건드려 문제가 된다. 비트 연산은 항상 unsigned 로 한다.

### [4] 클램프가 없으면

−200 의 32비트 표현은 0xFFFFFF38 이고 (2의 보수), 부호 없이 읽으면 4,294,967,096 이다. 타이머는 "카운터가 이 값보다 작은 동안 켠다"로 동작하므로, 카운터(0~1000)는 항상 이 값보다 작다. **듀티 100 %.** "속도를 줄여라"가 "전속력"이 된다.

M1 노트에 적은 내용(V5)을 바이트 수준에서 확인한 것이다. `clamp_duty` 한 줄이 왜 있는지, 그리고 그것을 지우면 테스트가 FAIL 하도록 만든 이유(M6의 B1)다.

## 4. 프로젝트와 연결

| 프로젝트 (시뮬레이션) | 실제 보드 |
|---|---|
| `sim/main.c` 의 `pwm_set` → `pwm.duty = duty / 1000.0` | `TIM1->CCR = duty;` |
| `sim/main.c` 의 `sensor_read` → `sensor_measure(&sensor, motor.w)` | `return ADC1->DR;` 또는 엔코더 카운터 레지스터 읽기 |
| `main.c` 가 1000걸음마다 `fw_tick()` 호출 | 타이머 인터럽트가 1 ms 마다 `fw_tick()` 호출 (A6) |
| `firmware/` 폴더 | **그대로** |

`hal.h` 로 경계를 그어 둔 덕분에, 보드로 옮길 때 새로 쓰는 것은 왼쪽 열의 세 줄뿐이다.

## 5. 질문

**Q1.** `TIM1->CR |= TIM_CR_ENABLE;` 은 한 줄이지만 CPU는 세 단계로 실행한다: 읽기, OR, 쓰기. 이 사이에 인터럽트가 끼어들어 같은 `CR` 의 다른 비트를 바꾸면 어떻게 될까?

<details><summary>▶ 답과 설명 보기</summary>

1. 메인 코드가 `CR` 을 읽는다 (값 A).
2. 인터럽트가 끼어들어 `CR` 의 3번 비트를 켜고 돌아간다. 이제 레지스터는 A | 0x8.
3. 메인 코드가 아까 읽은 **옛 값 A** 에 0번 비트를 OR 해서 쓴다. → 인터럽트가 켠 3번 비트가 **사라진다.**

"읽고-고치고-쓰기"가 한 덩어리로 실행되지 않기 때문이다. A6의 주제다. 그래서 어떤 칩은 "1을 쓰면 켜지는 전용 레지스터"와 "1을 쓰면 꺼지는 전용 레지스터"를 따로 둔다. 읽을 필요 없이 쓰기 한 번으로 끝나게 하려는 설계다.
</details>

**Q2.** 레지스터 구조체의 멤버 순서를 실수로 바꾸면(`ARR` 과 `CCR` 을 뒤바꿈) 컴파일러가 알려 줄까? 어떻게 막을 수 있을까?

<details><summary>▶ 답과 설명 보기</summary>

알려 주지 않는다. 컴파일러에게는 둘 다 `uint32_t` 멤버일 뿐이다. 듀티를 쓴다는 것이 주기를 바꾸게 되고, PWM 주파수가 이상해진다.

막는 방법:

- 칩 제조사가 주는 헤더 파일을 쓴다 (직접 옮겨 적지 않는다).
- 컴파일할 때 검사한다: `_Static_assert(offsetof(TimerRegs, CCR) == 0x08, "CCR offset");` 설명서의 오프셋과 다르면 컴파일이 실패한다.
- 패딩(A2)도 같은 문제를 만든다. 멤버가 전부 `uint32_t` 면 패딩이 없지만, 크기가 섞이면 생긴다.

"컴파일은 되는데 하드웨어가 이상하게 움직인다"는 버그는 오실로스코프 없이는 찾기 어렵다. 그래서 컴파일 단계에서 잡을 수 있는 것은 전부 거기서 잡는다.
</details>

**Q3.** `volatile` 을 붙이면 Q1의 문제(인터럽트가 끼어드는 것)도 해결되는가?

<details><summary>▶ 답과 설명 보기</summary>

아니다. 흔한 오해다.

- `volatile` 이 보장하는 것: 읽으라고 쓴 곳에서 **진짜로 읽는다**, 쓰라고 쓴 곳에서 **진짜로 쓴다.** (컴파일러가 생략하지 않는다.)
- 보장하지 않는 것: 읽기-고치기-쓰기 세 단계가 **끊기지 않고** 실행되는 것.

`a6_race.c` 의 `counter_plain` 에 `volatile` 이 붙어 있는데도 값을 잃어버리는 것이 그 증거다. 끊기지 않게 하려면 다른 장치(인터럽트 잠깐 끄기, 원자적 연산)가 필요하다. A6에서 본다.
</details>

  - 시뮬레이터 쪽(세상)이 매 걸음 `FAKE_TIM->CCR` 을 읽어 `pwm.duty` 로 쓴다.
  - 시뮬레이터 쪽이 제어 주기마다 `FAKE_ADC->DR` 에 센서 값을 써 두고, `sensor_read()` 는 그것을 읽기만 한다.
  - `firmware/` 는 한 글자도 고치지 않는다. 결과 CSV가 원래와 같은지 비교한다.

  이것을 하고 나면 "펌웨어는 레지스터에 쓰고 읽을 뿐이고, 그 너머는 하드웨어의 일"이라는 구조가 손에 잡힌다.
