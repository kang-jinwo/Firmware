# A2. 바이트, 엔디안, 포인터 연산, 구조체 패딩

실습: `python run.py lab a2_bytes` (코드: `advanced/labs/a2_bytes.c`)

메모리는 번호(주소)가 붙은 **바이트의 긴 줄**이다. `int`, `float`, 구조체는 그 바이트 몇 개를 "어떻게 읽을지"에 대한 약속일 뿐이다.

## 1. 먼저 예상한다

1. `uint32_t x = 0x12345678;` 은 4바이트다. 낮은 주소부터 `12 34 56 78` 로 놓일까, `78 56 34 12` 로 놓일까?
2. `int16_t neg = -2;` 의 2바이트는 16진수로 무엇일까? (M8의 2의 보수)
3. `int *p` 가 주소 1000 을 가리킨다. `p + 1` 은 주소 얼마인가?
4. 구조체에 `uint8_t, uint32_t, uint8_t, uint16_t` 가 순서대로 들어 있다. 멤버 크기의 합은 8이다. `sizeof` 는 얼마일까?

## 2. 실행 결과 (예)

```
[1] 엔디안: 0x12345678 은 메모리에 어떤 순서로 놓이나
  x          @ 0x7ffe9bd5a700 : 78 56 34 12
[2] 같은 바이트, 다른 해석
  neg(-2)    @ 0x7ffe9bd5a6fe : fe ff
  int16_t 로 읽으면 -2, uint16_t 로 읽으면 65534
  f(1.0f)    @ 0x7ffe9bd5a704 : 00 00 80 3f
[3] 포인터 연산: p + 1 은 주소를 몇 늘리나
  p     = 0x7ffe9bd5a720  (*p = 10)
  p + 1 = 0x7ffe9bd5a724  (*(p+1) = 20)
  주소 차이 = 4 바이트 = sizeof(int)
  arr[2] = 30,  *(arr + 2) = 30,  2[arr] = 30
  arr        @ 0x7ffe9bd5a720 : 0a 00 00 00 14 00 00 00 1e 00 00 00 28 00 00 00
[4] 구조체 패딩
  멤버 크기 합 = 8
  sizeof(struct Loose) = 12   offsets: a=0 b=4 c=8 d=10
  sizeof(struct Tight) = 8   offsets: b=0 d=4 a=6 c=7
  Loose      @ 0x7ffe9bd5a714 : 11 ee ee ee 22 22 22 22 33 ee 44 44
```

## 3. 설명

### 엔디안

여러 바이트짜리 값을 어느 쪽부터 놓는가의 약속이다.

- **리틀 엔디안**: 낮은 자리(78)를 낮은 주소에. PC(x86), 대부분의 ARM 마이크로컨트롤러.
- **빅 엔디안**: 높은 자리(12)를 낮은 주소에. 네트워크 통신 규격, 일부 CPU.

혼자 계산할 때는 몰라도 된다. 문제는 **바이트를 밖으로 내보낼 때**(통신, 파일, 다른 칩과 메모리 공유) 생긴다. 리틀 엔디안 칩이 `int` 를 그대로 보내고 빅 엔디안 칩이 그대로 받으면 0x12345678 이 0x78563412 가 된다.

### 같은 바이트, 다른 해석

`fe ff` 는 `int16_t` 로 읽으면 −2, `uint16_t` 로 읽으면 65534 다. 메모리에는 "이것은 부호 있는 수"라는 표시가 없다. **자료형은 컴파일러만 알고, 메모리는 모른다.**

M8에서 `pwm_set(-200)` 이 위험하다고 한 이유가 이것이다. −200 의 바이트를 부호 없는 레지스터가 읽으면 큰 양수다 (A5에서 직접 본다).

### 포인터 연산

`p + 1` 은 주소에 1을 더하는 것이 아니라 **"다음 칸"** 으로 간다. 한 칸의 크기는 가리키는 자료형의 크기다.

```
int *p      → p + 1 은 주소 + 4
char *p     → p + 1 은 주소 + 1
double *p   → p + 1 은 주소 + 8
MovingAvg *p → p + 1 은 주소 + sizeof(MovingAvg)
```

그래서 포인터에는 자료형이 붙어 있다. 주소만으로는 "한 칸이 몇 바이트인지", "그 바이트를 어떻게 읽을지"를 알 수 없다.

`arr[k]` 는 `*(arr + k)` 를 편하게 쓴 것이다. 덧셈은 순서를 바꿔도 되므로 `2[arr]` 도 컴파일된다 (쓰지는 말 것. 원리를 보여 주는 예일 뿐이다).

### 구조체 패딩

CPU는 4바이트짜리 값을 4의 배수 주소에서 읽을 때 가장 빠르다 (어떤 CPU는 아니면 아예 오류를 낸다). 그래서 컴파일러가 멤버 사이에 빈칸(패딩)을 넣어 줄을 맞춘다.

```
struct Loose (12바이트)             struct Tight (8바이트)
주소  0   1   2   3                 주소  0   1   2   3
     [a ][ee][ee][ee]                    [b           ]
      4   5   6   7                       4   5   6   7
     [b           ]                      [d      ][a ][c ]
      8   9  10  11
     [c ][ee][d      ]
```

`ee` 로 남은 칸이 패딩이다. 큰 멤버부터 놓으면 패딩이 줄어든다. RAM이 2 kB인 칩에서 이런 구조체 100개짜리 배열이라면 400바이트 차이다.

## 4. 프로젝트와 연결

- **원형 버퍼** `f->buf[f->idx]`: `f` 의 주소 + `buf` 의 오프셋 + `idx × 4` 바이트. 포인터 연산 두 번이 숨어 있다.
- **배열 범위**: `buf[64]` 는 `buf` 시작 + 256바이트, 즉 구조체에서 `buf` 다음 멤버인 `len` 의 자리다. `ma_init` 이 길이를 자르지 않으면, 길이 65짜리 필터는 `f->buf[64] = x` 로 **`len` 을 덮어쓴다.** C는 막지 않는다.
- **int16 오버플로** (M8 P5): 2바이트 `ff 7f` (32767) 에 1을 더하면 `00 80` 이고, 부호 있는 수로 읽으면 −32768 이다.
- **`Controller` 구조체**: `float`, `int`, `int32_t`, `int16_t` 가 섞여 있다. 패딩이 있을까? 아래에서 직접 확인한다.

## 5. 질문

**Q1.** `float f = 1.0f` 의 바이트가 `00 00 80 3f` 다. 정수 1 (`01 00 00 00`) 과 전혀 다르다. `int x = *(int *)&f;` 를 하면 x 는 얼마일까?

<details><summary>▶ 답과 설명 보기</summary>

0x3f800000 = 1,065,353,216. 바이트는 그대로 두고 **해석만** 정수로 바꾼 것이다.

`(int)f` 는 다르다. 이것은 값을 변환해서 1이 된다 (CPU가 변환 명령을 실행한다).

- `(int)f` : 값을 바꾼다. 바이트가 달라진다.
- `*(int *)&f` : 바이트는 그대로, 읽는 방법만 바꾼다.

뒤의 것은 C 규칙상 해서는 안 되는 일이기도 하다 (strict aliasing 위반). 바이트를 들여다보고 싶으면 실습의 `dump` 처럼 `unsigned char *` 를 쓰거나 `memcpy` 로 옮긴다.

float 의 비트 구조(부호 1, 지수 8, 가수 23)는 컴퓨터구조에서 배운다. 0x3f800000 을 직접 분해해 보면 좋다.
</details>

**Q2.** 통신으로 `uint32_t` 를 보낼 때 엔디안에 상관없이 항상 같은 바이트 순서가 되게 하려면 어떻게 쓰면 될까?

<details><summary>▶ 답과 설명 보기</summary>

메모리를 그대로 복사하지 말고, **시프트로 바이트를 하나씩 꺼낸다.**

```c
buf[0] = (uint8_t)(x >> 24);   /* 가장 높은 바이트부터 (빅 엔디안 순서) */
buf[1] = (uint8_t)(x >> 16);
buf[2] = (uint8_t)(x >> 8);
buf[3] = (uint8_t)(x);
```

`x >> 24` 는 "값"에 대한 연산이라 CPU의 엔디안과 상관없이 항상 가장 높은 자리를 준다. 받는 쪽도 같은 방식으로 조립한다. 구조체를 통째로 `memcpy` 해서 보내는 코드는 엔디안과 패딩 때문에 다른 칩에서 깨진다.
</details>

**Q3.** `sizeof(struct Loose)` 가 11이 아니라 12인 이유는? (마지막 멤버 `d` 는 오프셋 10에서 2바이트라 12에서 딱 끝나지만, 만약 `d` 가 없다면?)

<details><summary>▶ 답과 설명 보기</summary>

구조체 전체 크기는 **가장 큰 멤버의 정렬 단위(여기서는 4)의 배수**로 맞춰진다. `d` 가 없으면 9바이트가 아니라 12바이트다 (끝에 3바이트 패딩).

이유: 구조체의 배열을 만들었을 때 두 번째 원소의 `b` 도 4의 배수 주소에 와야 하기 때문이다. `p + 1` 이 `sizeof` 만큼 건너뛰므로, `sizeof` 자체가 정렬을 지켜야 한다.
</details>

## 6. 직접 해 볼 것

`advanced/my/` 폴더를 만들고 거기에 쓴다. `a2_bytes.c` 의 `dump` 함수를 복사해 써도 된다.

- [ ] `firmware/controller.h` 의 `Controller` 에 대해 `sizeof` 와 각 멤버의 `offsetof` 를 출력하는 프로그램을 쓴다. 멤버 크기를 손으로 더한 값과 비교해 패딩이 어디에 몇 바이트 있는지 찾는다. (함수 포인터 `step` 의 크기는 PC에서 8바이트다.)
- [ ] `int16_t v = 32767;` 을 `dump` 하고, `v = (int16_t)(v + 1);` 뒤에 다시 `dump` 한다. 바이트가 어떻게 바뀌는지 본다.
- [ ] Q2의 방식으로 `uint32_t` 를 4바이트 배열에 넣는 함수 `put_u32_be` 와 꺼내는 함수 `get_u32_be` 를 쓰고, 넣었다 꺼낸 값이 같은지 테스트한다 (M6의 `CHECK` 를 써서).
- [ ] `MovingAvg f;` 를 만들고 `ma_init(&f, 4)` 뒤에 `f.buf[64] = 99;` 를 일부러 써 본다. `f.len` 이 어떻게 되는지 출력한다. (경고가 나올 수 있다. 그 경고가 무슨 뜻인지 읽는다.)
