# A6. 인터럽트와 경쟁 상태

실습: `python run.py lab a6_race` (코드: `advanced/labs/a6_race.c`)

세 번째 질문 "**누가** 바꿀 수 있는가"의 가장 어려운 경우다: 두 실행 흐름이 같은 메모리를 건드릴 때.

## 1. 먼저 예상한다

두 스레드가 각각 `counter++` 를 100만 번 한다.

1. 끝난 뒤 `counter` 는 200만일까?
2. 아니라면 더 클까, 작을까? 매번 같은 값일까?

## 2. 실행 결과 (예)

```
run 1  expected 2000000
  plain  = 1934425   (잃어버린 횟수 65575)
  mutex  = 2000000
  atomic = 2000000
run 2  expected 2000000
  plain  = 1940179   (잃어버린 횟수 59821)
  ...
```

(숫자는 실행할 때마다 다르다. CPU 코어가 하나뿐인 환경에서는 잃어버리는 횟수가 훨씬 적거나 0일 수 있다. 그것도 중요한 관찰이다: **버그가 있어도 안 보일 수 있다.**)

## 3. 설명

### `counter++` 는 한 동작이 아니다

```
1. 메모리에서 counter 를 읽어 CPU 레지스터에 넣는다
2. 레지스터에 1을 더한다
3. 레지스터 값을 메모리에 쓴다
```

두 흐름이 이렇게 엇갈리면 한 번이 사라진다.

```
흐름 A                  흐름 B                counter (메모리)
읽기 (5)                                      5
                        읽기 (5)              5
더하기 (6)
                        더하기 (6)
쓰기 (6)                                      6
                        쓰기 (6)              6      ← 두 번 더했는데 1만 늘었다
```

이것을 **경쟁 상태**(race condition)라고 한다. 결과가 "누가 먼저 가느냐"는 타이밍에 달려 있다.

### 왜 무서운가

- **가끔만 일어난다.** 200만 번 중 6만 번, 3 %. 엇갈리는 순간이 수 나노초라서, 느린 주기로 도는 실제 펌웨어에서는 며칠에 한 번일 수 있다.
- **재현되지 않는다.** 같은 입력으로 다시 돌려도 타이밍이 달라 다른 결과가 나온다. `printf` 를 넣으면 타이밍이 바뀌어 사라지기도 한다.
- **테스트를 통과한다.** M6의 단위 테스트는 한 흐름으로만 함수를 부른다. 이 버그는 영원히 잡지 못한다.

### 펌웨어에서는: 인터럽트

마이크로컨트롤러에는 스레드가 없어도 같은 일이 생긴다. **인터럽트**: 하드웨어 사건(타이머가 찼다, 데이터가 도착했다)이 생기면 CPU가 하던 일을 **명령어 사이 어디서든** 멈추고, 정해진 함수(인터럽트 처리 함수, ISR)를 실행한 뒤 돌아온다.

```
메인 루프:  ... 명령 명령 명령 [멈춤]                    [이어서] 명령 명령 ...
인터럽트:                        └→ ISR 실행 → 돌아감 ─┘
```

메인 루프 입장에서는 **두 명령어 사이에 누군가 변수를 바꿔 놓고 간 것**이다.

실제 보드에서 이 프로젝트는 이렇게 된다.

```c
void TIM2_IRQHandler(void)      /* 1 ms 마다 타이머가 부른다 */
{
    fw_tick();
}

int main(void)
{
    fw_init(&cfg);
    while (1) {
        /* 통신으로 새 목표 속도를 받으면 */
        fw_set_target(new_target);
    }
}
```

`target_speed` 를 메인 루프가 쓰고 ISR(`fw_tick`)이 읽는다. `int` 하나를 쓰는 것은 32비트 CPU에서 명령어 하나라 괜찮다. 하지만:

- 8비트 CPU에서 16비트 `int` 를 쓰는 것은 명령어 **두 개**다 (낮은 바이트, 높은 바이트). 그 사이에 ISR이 끼어들면 "새 값의 낮은 바이트 + 옛 값의 높은 바이트"라는, **누구도 쓴 적 없는 값**을 읽는다. 목표 255 → 256 으로 바꾸는 중이라면 (0x00FF → 0x0100) 0x0000 이나 0x01FF(511)를 읽을 수 있다.
- 이득 `kp`, `ki` 를 **함께** 바꾸는 중에 끼어들면, 새 kp 와 옛 ki 의 조합으로 한 주기를 돈다. M5에서 본 것처럼 잘못된 조합은 출렁임을 만든다.

### 막는 방법

| 방법 | 어떻게 | 대가 |
|---|---|---|
| 인터럽트를 잠깐 끈다 | 끄기 → 공유 변수 건드리기 → 켜기 | 끈 동안 인터럽트가 늦어진다. **아주 짧게만** |
| 원자적 연산 | 읽기-고치기-쓰기를 CPU가 한 동작으로 (`atomic_fetch_add`) | 단순한 연산에만 된다 |
| 자물쇠 (mutex) | 한 번에 한 흐름만 들어오게 | ISR 안에서는 못 쓴다 (ISR은 기다릴 수 없다). RTOS의 작업 사이에서 쓴다 |
| 공유하지 않는다 | 한 변수는 한 흐름만 쓰게 설계. 주고받을 것은 큐로 | 설계를 미리 해야 한다. 가장 좋은 방법 |

실습의 `mutex` 와 `atomic` 이 항상 200만인 것이 2번, 3번이다.

### "한쪽만 쓰고 한쪽만 읽는" 원형 버퍼

프로젝트의 원형 버퍼(M7)는 사실 인터럽트와 메인 루프 사이에서 데이터를 넘기는 표준적인 구조이기도 하다.

- ISR은 `head` 번호만 바꾼다 (데이터를 넣고 `head` 를 한 칸 앞으로).
- 메인 루프는 `tail` 번호만 바꾼다 (데이터를 꺼내고 `tail` 을 한 칸 앞으로).
- `head == tail` 이면 비어 있다.

각 번호를 **한쪽만 쓰므로** 자물쇠 없이 안전하다 (번호 하나를 쓰는 것이 한 동작인 CPU에서). "공유하지 않는다"는 원칙을 자료 구조로 만든 것이다.

## 4. 프로젝트와 연결

- **M8 P8 (주기를 못 지킨다)**: 계산이 1 ms 를 넘으면 다음 타이머 인터럽트가 왔을 때 이전 `fw_tick` 이 아직 돌고 있다. 실제 칩에서 그러면 무슨 일이 생길까? `fw_tick` 안에서 `fw_tick` 이 다시 불린다. `ctrl.integ` 를 고치던 중에 같은 함수가 또 `ctrl.integ` 를 고친다. 경쟁 상태다. 시뮬레이터는 이것을 "건너뛴다"로 단순하게 흉내 냈을 뿐이다.
- **`static` 전역 변수** (A1): 프로그램 내내 살고 어디서든 닿는다는 것이, 여기서는 "ISR과 메인 루프가 둘 다 건드릴 수 있다"는 위험이 된다. `firmware.c` 가 `static` 으로 파일 안에 가두고 `fw_set_target()` 같은 함수로만 바꾸게 한 것은, **건드리는 곳을 한 군데로 모아** 보호 장치를 넣기 쉽게 하려는 것이다.
- 지금의 `fw_set_target` 에는 보호 장치가 없다. 시뮬레이션에서는 흐름이 하나뿐이라 괜찮았다. 실제 보드로 옮길 때 고쳐야 하는 곳이다.

## 5. 질문

**Q1.** `counter_plain` 에는 `volatile` 이 붙어 있다. 그런데도 값을 잃어버린다. 왜인가?

<details><summary>▶ 답과 설명 보기</summary>

`volatile` 은 "매번 진짜로 읽고 쓴다"만 보장한다. 읽기와 쓰기 **사이**에 다른 흐름이 끼어드는 것은 막지 못한다. (A5 Q3)

오히려 `volatile` 이 없으면 컴파일러가 100만 번의 `++` 를 "100만을 한 번에 더하기"로 바꿔서, 우연히 버그가 안 보일 수 있다. 최적화가 버그를 가린 것이다. 고쳐진 것이 아니다.
</details>

**Q2.** 인터럽트를 끄는 방법으로 `fw_set_target` 을 보호한다면 어떤 모양이 될까? 그리고 "끈 시간"은 왜 짧아야 하는가?

<details><summary>▶ 답과 설명 보기</summary>

```c
void fw_set_target(int target)
{
    disable_interrupts();       /* 칩마다 이름이 다르다 */
    target_speed = target;
    enable_interrupts();
}
```

끈 동안에는 타이머 인터럽트가 와도 `fw_tick` 이 시작되지 못하고 기다린다. 1 ms 주기가 그만큼 **밀린다** (지터). 끈 구간이 대입 한 줄이면 수십 나노초라 문제가 없다. 그 안에서 `printf` 나 긴 계산을 하면 M8의 P8이 된다.

규칙: 인터럽트를 끈 구간에서는 **값을 옮기기만** 한다. 계산은 밖에서 한다.

```c
int new_kp_q = compute(...);    /* 오래 걸리는 계산은 밖에서 */
disable_interrupts();
ctrl.kp_q = new_kp_q;           /* 안에서는 대입만 */
ctrl.ki_q = new_ki_q;
enable_interrupts();
```

이렇게 하면 kp 와 ki 가 항상 짝이 맞는 채로 바뀐다.
</details>

**Q3.** 이 버그를 테스트로 잡을 수 없다면, 무엇으로 막는가?

<details><summary>▶ 답과 설명 보기</summary>

**설계와 규칙**으로 막는다.

- 변수마다 "누가 쓰고 누가 읽는가"를 표로 적는다. 두 흐름이 닿는 변수는 전부 표시하고, 보호 방법을 정한다.
- 공유 변수는 함수 뒤에 숨긴다 (`fw_set_target`). 직접 건드리는 코드가 없으면 보호할 곳이 한 군데다.
- 코드 리뷰에서 그 표를 기준으로 본다.
- 도구: `gcc -fsanitize=thread` 는 PC에서 경쟁 상태를 실행 중에 찾아 준다.

M6에서 "테스트는 버그가 없음을 증명하지 못한다"고 했다. 여기가 그 한계가 가장 분명한 곳이다. 그래서 운영체제 과목은 동기화를 "테스트해 보니 된다"가 아니라 **"어떤 순서로 엇갈려도 맞다"를 논리로 따지는** 방식으로 가르친다.
</details>

- [ ] `firmware/firmware.c` 의 static 변수 네 개에 대해 "실제 보드라면 누가 쓰고 누가 읽는가" 표를 만든다 (메인 루프 / 타이머 ISR). 보호가 필요한 것에 표시한다.
- [ ] 한쪽만 쓰고 한쪽만 읽는 원형 버퍼를 직접 쓴다 (`advanced/my/spsc.c`): `put` (꽉 찼으면 실패), `get` (비었으면 실패). 한 스레드가 1~100000 을 넣고 다른 스레드가 꺼내서, 순서대로 빠짐없이 나오는지 확인한다. `head`, `tail` 은 `atomic_uint` 로 둔다.

<details><summary>▶ 세 번째 항목의 답</summary>

</details>
